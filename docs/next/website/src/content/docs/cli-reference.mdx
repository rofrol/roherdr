Herdr’s CLI talks to the running server over the same local socket API used by integrations and agents.

Most commands print JSON responses for deterministic automation in scripts.

## Launch and status

```bash
herdr                         # launch or attach to the default session
herdr --remote workbox        # attach through SSH, using local keybindings
herdr --default-config        # print default config
herdr update                  # download and install from the configured channel
herdr completion zsh          # generate a zsh completion script
herdr channel show            # print stable or preview
herdr channel set preview     # opt into preview builds
herdr channel set stable      # return a direct install to stable
herdr --version               # print version
```

Optional launch and update settings:

- Add `--session <name>` to use a named session instead of the default.
- Add `--remote-keybindings server` to remote attach to use server keybindings instead of local ones.
- Experimental live handoff requires explicit `--handoff` on `herdr --remote` or `herdr update`. It is not the normal setup or connection path; see [Updates](/docs/install/#update).

Status commands:

```bash
herdr status
herdr status server
herdr status client
```

API schema commands:

```bash
herdr api schema
herdr api schema --json
herdr api schema --output herdr-api.schema.json
```

`herdr api schema` prints a short summary of the socket protocol schema bundled
with the installed binary. Use `--json` for the full JSON Schema document, or
`--output PATH` to write that document to a file.

## Saved SSH machines

```bash
herdr machine list
herdr machine add workbox
herdr machine add workbox --label "Build machine"
herdr machine rename <profile-id> --label "New name"
herdr machine disable <profile-id>
herdr machine enable <profile-id>
herdr machine remove <profile-id>
```

In an interactive terminal, `machine add` discovers running sessions and lets you choose when several are running. No running sessions, or no Herdr installation, uses `default`; failed queries against an installed binary require an explicit choice. Add `--remote-session <name>` to skip discovery. Non-interactive commands use `default` unless that flag is supplied. `machine list` accepts optional `--json` for scripts. See [Connecting machines](/docs/connecting-machines/) for the full setup and connection guide.

`machine add` checks the remote installation's capabilities, installs or updates with approval only when needed, and starts the requested session's background server before saving. Compatible release versions do not need to match. Run setup in an interactive terminal when installation or restart approval is required; failed or cancelled setup does not save a profile. Replacing a running server requires explicit approval with a default answer of No, and stops its pane processes. `machine add` never enables experimental handoff implicitly.

Changes apply automatically to open local Herdr clients, normally within a second. Added or enabled machines connect in the background; renaming does not reconnect. Removing or disabling disconnects only that machine and leaves its remote sessions running. Removing the machine you are viewing returns to Local, or shows Local as unavailable until it reconnects. Each profile stores an opaque ID, label, SSH target, explicit remote session, and enabled state in client state. Herdr does not store passwords, private keys, or other SSH credentials.

Use `herdr machine status [<label-or-id>] [--json]` for fresh, noninteractive SSH and remote Herdr checks. `reachable` describes this check, not a TUI's current connection. Use `herdr machine reconnect <label-or-id>` in a terminal for SSH authentication and verification; it does not install or update Herdr. Open clients retry failed connections within 30 seconds. Clicking `! auth` or `! error` shows the latest error and CLI guidance; collapsed sidebars show `!`. See [Recovering SSH authentication](/docs/connecting-machines/#recovering-ssh-authentication) for platform limits. For remote setup, use `herdr --remote workbox`, adding `--session <name>` only for a named session.

Workspace, tab, pane IDs, and agent names belong to a single server. Selecting a machine in the UI does not retarget CLI commands. Use the global **prefix** `--machine <label-or-id>` to route API commands to a saved SSH machine:

```bash
herdr --machine "Build machine" agent list
herdr --machine <profile-id> pane list
herdr --machine "Build machine" agent prompt w1:p1 "review this change"
herdr --machine "Build machine" worktree create --cwd /srv/project --branch review
```

The selector must match an enabled saved profile ID or a unique, case-sensitive label, not an arbitrary SSH hostname. The saved remote session is used; combining `--machine` with `--session` or `--remote` is an error. Without the prefix, commands retain their existing local session/socket behavior.

Supported commands are `workspace`, `worktree`, `tab`, `pane`, `notification`, `agent` (except `attach` and local `explain --file`), `api snapshot`, `status server`, and API-backed plugin commands (`link`, `unlink`, `enable`, `disable`, `list`, `action`, `log`, `pane`). Server commands support `stop`, `reload-config`, `agent-manifests`, and `reload-agent-manifests`. Local installation/configuration commands, plugin installation, session management, and interactive terminal attachment are not forwarded.

Requests and responses travel through the JSON API over non-interactive SSH; API payloads are not interpolated into the SSH shell command. No open TUI is required, and the bridge never installs, starts, or restarts a server. Update the local CLI and remote Herdr installation to support machine forwarding, and keep the running remote server's API protocol compatible. Authentication, unavailable machines, and incompatible versions fail without falling back to Local. Requests are not automatically retried after connection failure.

Local pane IDs are not inherited by remote commands. Use explicit remote IDs; `--current` cannot refer to the caller's local pane. Remote worktree paths must be absolute, `~`, or start with `~/` (expanded on the server); plugin link paths must be absolute. The prefix targets one machine at a time; combined listings and routing through another TUI's connections are not included.

## Shell completions

```bash
herdr completion zsh
herdr completions zsh
herdr completion bash
herdr completion fish
herdr completion powershell
herdr completion elvish
```

`completion` prints the script to stdout. `completions` is an alias. For a
temporary zsh session, load the script directly:

```bash
source <(herdr completion zsh)
```

For a persistent zsh setup, write the generated `_herdr` function somewhere on
your `fpath` before `compinit` runs:

```bash
mkdir -p ~/.zfunc
herdr completion zsh > ~/.zfunc/_herdr
```

Then make sure your `.zshrc` contains:

```zsh
fpath=(~/.zfunc $fpath)
autoload -Uz compinit
compinit
```

## Server

```bash
herdr server
herdr server stop
herdr server reload-config
herdr server agent-manifests [--json]
herdr server update-agent-manifests [--json]
herdr server reload-agent-manifests
```

`herdr server` runs the headless server explicitly. Use it for supervised or service-style setups. `reload-config` applies reloadable settings without restarting panes. `agent-manifests` shows the active agent detection manifest sources, cached remote versions, and last remote update results. `update-agent-manifests` fetches remote manifest updates immediately, reloads them into the running server, and prints the updated manifest status; pass `--json` for the raw status response. `reload-agent-manifests` reloads agent detection manifests into the running server after local override edits.

## Notifications

```bash
herdr notification show <title> [--body TEXT] [--position top-left|top-right|bottom-left|bottom-right] [--sound none|done|request] [--pane PANE_ID]
```

`notification show` uses the configured `[ui.toast]` delivery. `--position` only affects in-app Herdr toasts. `--sound` defaults to `none`; `done` and `request` play the existing finished and needs-attention sounds only when the notification is shown. `--pane` sends `notification.show_for_pane`: clicking the desktop notification focuses that pane's tab, or its workspace once the tab is closed.

herdr session list [--json]

Use `default` as the session name when you need to stop the default session explicitly.

## Workspaces

```bash
herdr workspace list
herdr workspace create [--cwd PATH] [--label TEXT] [--env KEY=VALUE] [--focus] [--no-focus]
herdr workspace get <workspace_id>
herdr workspace focus <workspace_id>
herdr workspace rename <workspace_id> <label>
herdr workspace report-metadata <workspace_id> --source ID [--token NAME=VALUE] [--clear-token NAME] [--seq N] [--ttl-ms N]
herdr workspace close <workspace_id> [--group]
herdr workspace bookmark <workspace_id>
herdr workspace unbookmark <workspace_id>
```

Create a workspace without stealing focus:

```bash
herdr workspace create --cwd ~/project --label api --no-focus
```

A workspace is a top-level project or work context. Creating one also creates its first tab and root pane. The JSON response exposes their IDs as `.result.workspace.workspace_id`, `.result.tab.tab_id`, and `.result.root_pane.pane_id`.

## Worktrees

```bash
herdr worktree list [--workspace ID | --cwd PATH] [--trust-repository]
herdr worktree create [--workspace ID | --cwd PATH] [--branch NAME] [--base REF] [--path PATH] [--label TEXT] [--focus] [--no-focus] [--trust-repository]
herdr worktree open [--workspace ID | --cwd PATH] (--path PATH | --branch NAME) [--label TEXT] [--focus] [--no-focus] [--trust-repository]
herdr worktree remove --workspace ID [--force] [--trust-repository]
```

Worktrees are normal Herdr workspaces with Git checkout provenance. `worktree create` creates a Git worktree checkout, opens it as a workspace, and groups it with the parent repo workspace. If `--branch` names an existing local branch, Herdr checks it out; otherwise it creates the branch from `--base` or `HEAD`. Without `--path`, Herdr creates the checkout under `<worktrees.directory>/<repo>/<branch-slug>`.

`workspace close` closes only Herdr state. Closing a primary workspace while linked-worktree workspaces are open requires `--group`; without it, the command leaves the group open and returns `workspace_group_close_required`. To delete the checkout, run `worktree remove`. It runs `git worktree remove`, never deletes the branch, and requires `--force` when Git refuses a dirty checkout.

Git rejects repositories owned by another user by default. If you have independently verified the repository, pass `--trust-repository` to trust its resolved path for that command only. Herdr does not change your Git configuration.

## Tabs

```bash
herdr tab list [--workspace <workspace_id>]
herdr tab create [--workspace <workspace_id> | --parent <tab_id>] [--cwd PATH] [--label TEXT] [--env KEY=VALUE] [--focus] [--no-focus]
herdr tab get <tab_id>
herdr tab focus <tab_id>
herdr tab rename <tab_id> <label>
herdr tab close <tab_id>
herdr tab parent <tab_id> <parent_tab_id>|none
herdr tab status <tab_id> running|succeeded|failed|none
```

`tab parent` nests a tab under a top-level tab of the same workspace (one level deep); `none` makes it top-level again. While a workspace has child tabs, the TUI shows a second row with the active tab's own entry and its children, and a parent tab summarises its children's statuses, e.g. `⧖ 1 !2 ✓3`. `tab status` sets the status a client shows as an icon. The server refuses to close a tab that has child tabs (`tab_has_children`): in a terminal, `herdr tab close` asks and then closes the children first, and the TUI asks the same way. Closing a parent's last pane instead leaves its children as top-level tabs.

A tab is another terminal layout inside a workspace. Without `--workspace`, `tab create` uses the active workspace and fails if none exists. `--parent` creates the tab already nested under that top-level tab, in its workspace. Its JSON response exposes `.result.tab.tab_id` and `.result.root_pane.pane_id`. Closing a workspace's last tab also closes the workspace, matching the TUI close-tab action. If `confirm_close` is enabled and closing the tab would also close a whole worktree group, `tab close` returns a `confirmation_required` error instead.

Closing an active tab focuses the previous tab at the same level, or the next one if there is no previous sibling. Closing an only child returns to its parent. Closing a main tab does not jump into another tab's nested jobs. Closing an inactive tab leaves the active tab unchanged.

With `ui.confirm_close` enabled, the TUI asks for confirmation before closing a workspace's last tab from a keybinding or the tab menu. Ordinary CLI/API tab closes remain immediate.

With `ui.confirm_close_running` enabled (the default), the TUI also asks before closing a tab, pane or workspace that has running work: a tab marked running with `tab status`, any agent still running in it (working, waiting for an answer, idle or done), or a program the pane's shell started, such as a build or `lazygit`. Resuming an agent later does not bring back an unsent draft or its background tasks, so idle agents count too. The dialog names what the close would stop, e.g. `claude idle in herdr · 2 bg`. This works independently of `ui.confirm_close`, and CLI/API closes remain immediate.

Workspace and tab creation, and pane splitting, leave focus unchanged by default. `--focus` selects the new layout; `--no-focus` states the default explicitly. Without `--cwd`, new terminals follow the configured `terminal.new_cwd` policy, which follows the source pane or workspace by default. Each `--env KEY=VALUE` adds or replaces that variable in the new root shell.

## Panes

```bash
herdr pane list [--workspace <workspace_id>]
herdr pane current [--pane ID|--current]
herdr pane get <pane_id>
herdr pane layout [--pane ID|--current]
herdr pane process-info [--pane ID|--current]
herdr pane neighbor --direction left|right|up|down [--pane ID|--current]
herdr pane edges [--pane ID|--current]
herdr pane focus --direction left|right|up|down [--pane ID|--current]
herdr pane resize --direction left|right|up|down [--amount FLOAT] [--pane ID|--current]
herdr pane zoom [<pane_id>|--pane ID|--current] [--toggle|--on|--off]
herdr pane rename <pane_id> <label>|--clear
herdr pane input [<pane_id>|--pane ID|--current] --right-click herdr|pane
herdr pane split [<pane_id>|--pane ID|--current] --direction right|down [--ratio FLOAT] [--cwd PATH] [--env KEY=VALUE] [--right-click herdr|pane] [--focus] [--no-focus]
herdr pane swap --direction left|right|up|down [--pane ID|--current]
herdr pane swap --source-pane ID --target-pane ID
herdr pane move <pane_id> --tab <tab_id> --split right|down [--target-pane ID] [--ratio FLOAT] [--focus|--no-focus]
herdr pane move <pane_id> --new-tab [--workspace ID] [--label TEXT] [--focus|--no-focus]
herdr pane move <pane_id> --new-workspace [--label TEXT] [--tab-label TEXT] [--focus|--no-focus]
herdr pane close <pane_id>
```

For pane commands that accept `--current`, Herdr uses the calling pane's
`HERDR_PANE_ID` when the command runs inside a Herdr pane. For `pane split`,
an explicit pane id or `--pane ID` splits that pane. An omitted target splits
the calling pane when `HERDR_PANE_ID` is available, otherwise the focused pane.
`--current` requires a calling pane and errors when `HERDR_PANE_ID` is unavailable.
The split response exposes the new pane ID as `.result.pane.pane_id`.

`pane input --right-click pane` forwards unmodified right-click gestures to a
mouse-reporting pane application. `herdr` restores the default pane menu.
Right-clicking the pane frame still opens Herdr's menu. `pane split
--right-click pane` applies the same policy to the new pane at creation.

After `pane move`, use `.result.move_result.pane.pane_id` for later commands. A cross-workspace move changes the workspace-qualified pane ID; the prior value remains at `.result.move_result.previous_pane_id`. The running process keeps its launch-time `HERDR_PANE_ID`, `HERDR_TAB_ID`, and `HERDR_WORKSPACE_ID`; Herdr retains the old pane ID as an alias for that terminal, so pane commands using `--current` still resolve it. A live agent name follows the terminal and continues to resolve after the move.

Read output:

```bash
herdr pane read <pane_id> [--source visible|recent|recent-unwrapped|detection] [--lines N] [--format text|ansi] [--ansi] [--raw]
herdr pane read <pane_id> --source visible --ansi
herdr pane read <pane_id> --source recent-unwrapped --lines 120
```

`pane read` prints UTF-8 terminal text directly. ANSI escapes are stripped by default; use `--format ansi` or `--ansi` to preserve them where the source exposes styling. The `detection` source is always plain text. For recent sources, `--lines N` selects the last N rendered terminal rows before optional unwrapping; without it, reads default to 80 rows. For `visible` and `detection`, omitting `--lines` returns the full snapshot, while specifying it keeps the last N newline-delimited lines. `agent read` uses the same output and line behavior.

Send input:

```bash
herdr pane send-text <pane_id> <text>
herdr pane send-keys <pane_id> <key> [key ...]
herdr pane run <pane_id> <command>
```

`<key>` uses Herdr key-combo syntax: plain printable keys such as `a`,
special keys such as `enter`, `tab`, `esc`, `backspace`, `left`, `right`,
`up`, and `down`, modifier chords such as `ctrl+h`, `control+j`, `alt+x`,
and `shift+tab`, function keys such as `f1`, and named punctuation such as
`minus`, `plus`, and `backtick`. Legacy `C-c` and `c-c` are accepted as
aliases for `ctrl+c`.
`esc` is the canonical spelling; `escape` is also accepted.

`pane run` honors live bracketed-paste mode and submits text plus Enter atomically. Prefer it over `send-text` plus `send-keys Enter` for commands; the separate send operations remain low-level and non-submitting.

Report agent state from custom hooks:

```bash
herdr pane report-agent <pane_id> \
  --source ID \
  --agent LABEL \
  --state idle|working|blocked|unknown \
  [--message TEXT] \
  [--seq N] \
  [--agent-session-id ID] \
  [--agent-session-path PATH] \
  [-- RESUME_COMMAND...]

herdr pane report-agent-session <pane_id> \
  --source ID \
  --agent LABEL \
  [--seq N] \
  [--agent-session-id ID] \
  [--agent-session-path PATH] \
  [--session-start-source SOURCE] \
  [-- RESUME_COMMAND...]

herdr pane release-agent <pane_id> \
  --source ID \
  --agent LABEL \
  [--seq N]

herdr pane forget-agent-session <pane_id> \
  --source ID \
  --agent LABEL \
  --seq N \
  (--agent-session-id ID | --agent-session-path PATH)
```

`report-agent-session` updates native session identity without reporting lifecycle state. `release-agent` ends that source's lifecycle authority when its agent process exits. `forget-agent-session` tells Herdr the user ended that session, so a server restart does not resume it (see [`pane.forget_agent_session`](/docs/socket-api/)).

Arguments after `--` are the command Herdr runs to resume this session after a server restart. The first argument must be a plain command name on `PATH`, and no argument may contain an apostrophe.

`pane get`, `pane list`, `agent get`, and `agent list` include a read-only `agent_session` object when an official integration has reported a native session reference. If no native session reference is stored, the field is omitted.

Those commands include `foreground_cwd` when Herdr can resolve the cwd of the foreground process controlling the pane. The `cwd` field remains the pane/workspace cwd used for labels and follow-cwd behavior.

`pane get` and `pane list` include `scroll` when terminal scroll metrics are available. `scroll.offset_from_bottom == 0` means the pane is at the bottom of its scrollback.

Report display-only pane metadata without taking over semantic state:

```bash
herdr pane report-metadata <pane_id> \
  --source ID \
  [--agent LABEL] \
  [--applies-to-source ID] \
  [--title TEXT|--clear-title] \
  [--display-agent TEXT|--clear-display-agent] \
  [--state-label STATUS=TEXT] \
  [--clear-state-labels] \
  [--token NAME=VALUE] \
  [--clear-token NAME] \
  [--seq N] \
  [--ttl-ms N]
```

`STATUS` is one of `idle`, `working`, `blocked`, `done`, or `unknown`. `--agent` and `--applies-to-source` guard only `--title`, `--display-agent`, and `--state-label`. They do not guard token patches; token reporters own clearing or TTL refresh. Use `--display-agent` to change the visible name.

Metadata text is normalized before storage. Herdr trims surrounding whitespace, removes control characters, and caps `--title`, `--display-agent`, each `--state-label`, and token values at 80 characters. Empty normalized token values clear that key.

`--token` patches one named display value; `--clear-token` removes one. Unmentioned tokens remain unchanged. Pane tokens are available to Agent sidebar rows as `$name`; workspace tokens are available to Space rows. TTL applies independently to the token keys updated by that call.

`--source` and `--applies-to-source` must be 80 characters or fewer and may contain only ASCII letters, digits, colon, dot, underscore, and hyphen. `--ttl-ms` makes metadata expire automatically and must be between `1` and `86400000` milliseconds. Omit it for metadata that should stay until replaced, cleared, or the pane closes. `--seq` lets Herdr ignore stale reports from the same `--source`; stale reports are accepted by the API but ignored by pane state. A pane or workspace accepts sequenced token reports from at most 32 distinct sources during its lifetime; clearing or expiry does not release those source slots.

## Agents

For the pane-versus-agent model and complete orchestration examples, see [Agent automation](/docs/agent-automation/).

```bash
herdr agent list
herdr agent get <target> [--global]
herdr agent read <target> [--source visible|recent|recent-unwrapped|detection] [--lines N] [--format text|ansi] [--ansi] [--global]
herdr agent send-keys <target> <key> [key ...] [--global]
herdr agent prompt <target> <text> [--wait] [--until STATUS]... [--timeout MS] [--global]
herdr agent rename <target> <name>|--clear [--global]
herdr agent focus <target> [--global]
herdr agent awaiting-reply [--pane PANE_ID] [QUESTION]
herdr agent limited [--pane PANE_ID] usage|credits [MESSAGE]
herdr agent set-task [--pane PANE_ID] <task>|--clear
herdr agent wait <target> [--until STATUS]... [--timeout MS] [--global]
herdr agent wait-turn <request_id>
herdr agent attach <target> [--takeover] [--global]
herdr agent start <name> --kind KIND --pane ID [--timeout MS] [-- <agent-args...>]
herdr agent explain <target> [--json|--verbose] [--global]
herdr agent explain --file PATH --agent LABEL [--json|--verbose]
```

Agent targets are either a live agent name or the pane ID that currently hosts the agent. Terminal IDs and bare agent-kind labels are not agent targets. Agents started through `agent start` require a name; manually launched agents remain unnamed and use their pane ID.

Inside a Herdr pane, a name resolves in the caller's workspace (`HERDR_WORKSPACE_ID`) first, so each workspace can have its own `reviewer`. A name the caller's workspace does not use resolves across all workspaces when it is unique there. Pass `--global` to `agent get`, `read`, `send-keys`, `prompt`, `rename`, `focus`, `wait`, `attach`, or `explain` to look a name up in every workspace at once; a name used in several workspaces is then ambiguous. Callers outside a pane and `--machine` targets always resolve globally. A name that matches several agents where it is looked up returns `agent_target_ambiguous` with the candidates. Pane ID targets are unaffected.

`agent start` activates an existing available shell pane: the pane's interactive shell must own the foreground, with no foreground command, editor, or agent running. Topology must be created separately. Names are unique among the live agents of a workspace and must match `[a-z][a-z0-9_-]{0,31}`. The kind selects Herdr's canonical interactive executable, while arguments after `--` are passed to that executable. Supported kinds are `pi`, `claude`, `codex`, `gemini`, `cursor`, `devin`, `agy`, `cline`, `omp`, `mastracode`, `opencode`, `copilot`, `kimi`, `kiro`, `droid`, `amp`, `grok`, `hermes`, `kilo`, `qodercli`, `qwen`, `letta`, `maki`, and `muse`. A name follows the current pane occupant and is cleared when that agent exits, is released, or is replaced. Temporary detection uncertainty does not clear it.

A successful start returns only after the expected agent owns the same terminal and is ready for interactive input. If detection reports `blocked` during startup, the command returns `agent_not_ready` immediately. The name remains available for `agent read` and `agent send-keys`, and becomes ready for prompts after detection reports `idle`. The default startup timeout is 30000 milliseconds; explicit values must be greater than 3000 and no more than 300000.

`agent prompt` honors live bracketed-paste mode and writes text followed by delayed Enter as one ordered submission, including while the agent is working. Without `--wait` it uses `agent.prompt_confirmed` and returns only once the agent shows it accepted the prompt: the prompt's turn report for Claude (its `UserPromptSubmit` hook) and Pi, the agent's state turning `working` for agents without turn reports, or at once when the agent was already `working` and queues it. A dialog that appears after typing returns `agent_prompt_blocked` naming the dialog; the prompt is never typed twice, so check the agent before sending it again. Without an acknowledgement it waits until the agent exits or the command is interrupted; against an older server it says so on stderr and only acknowledges the writes. On Windows, Codex receives a paste boundary before Enter so submission does not depend on prompt size; the caller timeout includes submission time. If the agent is already `blocked`, it returns `agent_blocked` without sending input, naming the dialog when Herdr recognizes it. With `--wait`, a prompt sent from another non-working state first waits for the same acknowledgement, with no time limit of its own; unrelated `idle`, `done`, or session changes do not complete the wait. A dialog that appears before the acknowledgement returns `agent_prompt_blocked` naming it, unless `blocked` is one of the requested states, which then matches as before. If the caller timeout expires before the acknowledgement, Herdr returns `agent_prompt_stalled`; after it, the normal `timeout` error. After the acknowledgement, it waits for the first requested settled status. That screen-state wait does not track individual turns: if the agent is already working, completion of that active turn may satisfy it. It is used with `--until` and for agents whose integration does not report turns. Without `--until`, an agent that reports turns (Claude, Pi) is followed instead: `--wait` prints `herdr: waiting for the turn of prompt request <id>` on stderr, then returns when the turn this prompt started ends and prints how it ended (`agent_turn_ended` with `reason` `finished`, `failed` with its `error`, `interrupted` after an explicit interrupt, `unknown` when another turn started first with no signal saying why, `exited` or `unknown_request`); it exits 0 only for `finished`. `agent wait-turn <request_id>` waits for that same request again, for example after the waiting command was cut off; it has no timeout, because every outcome, including a server restart that lost the request (`unknown_request`), ends it. With `--timeout`, `--wait` instead returns the prompt's `prompt_request` when the turn ends, and a timeout names the request's state (`accepted` or `working`). `--until` narrows the matching states and is rejected unless `--wait` is also present. Standalone `agent wait` returns immediately when the current status matches. Both default to `idle`, `done`, or `blocked`; use `--until unknown` explicitly when needed.

`idle` and `done` both mean ready for input. The CLI/API uses the server's seen state: `done` is idle but not yet marked seen, explicit `pane focus` / `agent focus` commands mark the target seen, and reads do not. Each TUI client tracks viewed completions independently, so its Done badge can differ from the CLI or another client. `blocked` means Herdr recognized an approval or question UI. `unknown` means an agent is present but Herdr cannot classify it confidently, not that its work succeeded.

`agent awaiting-reply` is run by the agent itself, as its last command right before it ends a turn with a plain-text question or decision for the user. It reports the pane in `--pane`, or the caller's `HERDR_PANE_ID`, and the question in a few words when given (`herdr agent awaiting-reply "Install now?"`), which the header's `?` list shows under the agent. The agent then shows `awaiting_reply: true` while it is idle and keeps its Done mark in the TUI, even after the pane is viewed, until someone types into the pane or the agent shows a prompt. The Claude Code integration asks Claude to run it. The user's side is `herdr pane dismiss-question [PANE_ID]...`, which forgets the question of the given panes (or the caller's) without typing into them. `agent set-task` is also run by the agent itself: a few words naming the task it starts, shown as the tab's name ahead of the terminal title (see `pane.report_task` in the socket API); `--clear` forgets it. `agent limited` is run by an agent's hook when a limit ended its turn: `usage` for a usage or rate limit that resets on its own, `credits` when waiting does not help; the `?` list then shows the agent as `limited · resets 14:32` (see `pane.report_limit` in the socket API).

`agent send-keys` sends logical terminal keys such as `enter`, `up`, `esc`, or `ctrl+c`. Herdr validates every key before writing any bytes. `agent read` reads the resolved terminal stream, and `agent rename` names an already detected agent.

`agent explain` asks the running server to classify the same bottom-buffer detection snapshot used by screen detection, so live output reflects the server's active manifest cache. Because this uses the `agent.explain` socket method, restart or hand off to an updated server after upgrading Herdr before using live explain. Use `--file PATH --agent LABEL` to explain a saved fixture locally instead. The default output shows the agent, final state, manifest source and version, matched rule with its region evidence, and any fallback, skip, or warning reasons. Add `--verbose` for visible evidence flags, cached remote version, local override shadowing, remote update status, and the full evaluated-rules list with matcher and region evidence. Add `--json` for issue reports or tests.

Use `pane send-text`, `pane send-keys`, `pane run`, and `terminal attach` for ordinary terminals, servers, tests, shells, or low-level terminal control. Use `pane run` when you want to submit a command with Enter.

Headless Claude workers run without a pane; the server owns them (see `worker.*` in the socket API):

```bash
herdr worker start [--name TASK] [--cwd DIR] [--model MODEL] [--workspace ID] [--item ID] [--folder-slot NAME --branch BRANCH [--base REF] [--fresh-build]] (--prompt TEXT | <prompt>)
herdr worker status <worker_id>
herdr worker list
herdr worker runs [--item ID] [--repo DIR]
herdr worker wait <worker_id> [--exit | --attention [--after SEQ]]
herdr worker ack <worker_id> <seq>
herdr worker obligations [--pane PANE_ID]
herdr worker escalate <worker_id> --request REQUEST_ID
herdr worker verify <worker_id> --base SHA --message SUBJECT --paths GLOB... [--cmd COMMAND] [--generated PATH=COMMAND]...
herdr worker prompt <worker_id> <text>
herdr worker interrupt <worker_id> [--turn SEQ]
herdr worker stop <worker_id>
herdr worker kill <worker_id> [--force]
herdr worker answer <worker_id> --request REQUEST_ID [--message TEXT] allow|deny|<choice>...
herdr worker log [--follow] <worker_id>
herdr worker take-over [--force] <worker_id>
herdr worker drain <start [--reason TEXT]|status|cancel>
herdr worker wait-drained
```

`worker start` defaults `--cwd` to the current directory, `--name` (the worker's line in the sidebar) to the prompt's first line and `--workspace` (the space the line is listed under) to the caller's space. `--item` names the TODO item the worker works on, by its stable id (`t-` and 8 characters a-z and 2-7, as `scripts/todo_edit.py` writes it at the end of the item's first line); any other value is refused. `worker runs` lists every worker's run (one worker process, from start to end; a `worker prompt` adds turns to the same run) grouped by its item within the repository of its directory (the parent of the git common directory, the same for every worktree), so ids of different repositories never mix: each run's start and end, outcome (`running`, `finished`, `failed`, `exited`, `lost` or `degraded`), turns, the commit shas its replies named on `WORKER-DONE <sha>` lines, the questions it asked and its journal. Runs started without `--item` are listed as `unassigned`, never grouped by name. Each item also carries its `title`, its first line in the repository's `TODO.md` without the box and the id, as `worker start --item` found it there (the latest run's), so a finished item that has left the file keeps it; for runs started without one stored, it is read from `TODO.md` when listed. `--item` keeps one item's runs, `--repo DIR` those of DIR's repository. The sidebar lists only live workers: a running one, and an ended one until its owner acknowledges the end (`worker ack`), so a crash or a result waiting for review stays in view; a worker without an owner leaves at its end. Ended work is reached through its item: the line of a tab with the role `coordinator` has an `Items` button for the repository of that tab's directory, whose badge counts that repository's items with a running worker and, after `·`, those with an ended run not acknowledged yet (`Items 3·1!`). It opens a list of the items with runs, those in progress first, by title and id (the id alone when no title is known), an `Unassigned` entry, and, from `herdr history`'s records, the 20 most recently finished items (their latest record is the close), grouped by the day they closed. An item opens its history: its timeline (the claim with the item's text, each attempt of the claim's run with its worker, verdict, the coordinator's decision and the commit it landed, the notes, the close with its decision and the follow-up items, each of which opens its own history; long texts are cut at 12 lines), then its worker runs no attempt names (worker, start and end, outcome, the latest `worker verify` verdict, turns, questions, commits); a run or an attempt opens its worker's log. Times are local. The list asks the server for the runs, then the records, when it opens, and an item for its timeline when it opens, never in the background. `worker verify` decides whether a worker's commit is ready, instead of taking its `WORKER-DONE` line's word: herdr runs it in the worker's directory, outside the worker's sandbox, and checks that the branch has exactly one commit since `--base` (each is reported) and descends from it, that its message is exactly `--message` with no body or trailers (a `Co-Authored-By` line fails it), that the paths it changes match the git glob pathspecs after `--paths` (`'src/**'`, `AGENTS.md`), that the worktree is clean apart from ignored files, and that no process of the worker remains (stop it first). Then, only in a clean worktree, each `--generated PATH=COMMAND` runs COMMAND and PATH must equal its committed bytes, and `--cmd` (run with `sh -c`, for example `cargo nextest run -E 'test(/workers::/)'`) must exit 0; both run as long as they take, and the worktree is restored to its head afterwards. Both run with the environment of the shell that ran `worker verify` (without its `HERDR_*` variables), not the herdr server's, which may lack what your shell profile sets, such as `ZIG` or `PATH`; through `--machine` the remote server's own environment is used. The verdict is `verified` only when every check passed, `failed` when one failed, and `unavailable` when one could not run (git missing, a command not found or ended by a signal), which is never a pass. A command that fails on its build environment rather than on the project is `unavailable` too: its output shows a toolchain error (Zig's `does not meet the required build version`, `requires Zig `, `zig executable not found`, cargo's `error: no such command: `, rustup's `error: toolchain '...' is not installed`, a missing linker, or a shell's `command not found`) and no sign of the project's own failure (a rustc `error[E...]`, `test result: FAILED` or nextest's `FAIL [`), which keeps it `failed`. It prints the verdict with each check's evidence (what failed, the output's last lines, the commit shas), records it as the worker's `verification` event and stores it with the run; it exits 0 only when verified, 1 when failed, 3 when unavailable. With `--folder-slot NAME` the worker runs in the persistent git worktree `../herdr-worktrees/NAME` next to the repository of `--cwd` instead (created at `--base` on first use), one worker at a time, so its `target/` and Zig cache (`target/zig-cache`) stay warm and only the changes compile inside the sandbox. Before each start herdr refuses while a worker still runs there (stop it first), ends processes an earlier worker left running in the folder, refuses when `git status` shows changes, checks out the new branch `--branch` (it must not exist yet) from `--base` (default `master`) and removes untracked files that are not ignored (`git clean -fd`). `--fresh-build` removes the slot's `target/` first. Before that herdr runs the repository's `scripts/target_sweep.py slot`, when the slot has it: the sweep `just sweep` runs, with a 10 GiB limit for the slot's `target/` (it builds one branch at a time, so older test binaries are dead weight), giving up while a cargo build holds its lock; when less than 15 GiB stay free even after removing the whole `target/`, or a build holds the lock, the start is refused with why. `worker wait` returns at the end of the current turn, or with `--exit` when the process ended. With `--attention` it returns at once or at the first of a pending question, a turn's end or the worker's end, with the `reason`, the pending `questions` and `seq`; `--after SEQ`, given the `seq` it returned, skips what that reply already showed, so a coordinator waits in a loop with `herdr worker wait <id> --attention --after <seq>` and is woken once per new question or turn end. `worker start` makes the caller's pane (`HERDR_PANE_ID`) and agent session (`CLAUDE_CODE_SESSION_ID`) the worker's owner. `worker obligations` lists the workers a pane owns (`--pane`, default the caller's) that have an event their owner has not acknowledged: an unanswered question, a turn end or the worker's end, each with its `reason` and `seq`. A question of an owned worker waits quietly for its owner: the header's `?` list shows it dim as awaiting the coordinator, with how long ago the coordinator's last event was, and does not count it. `worker escalate <id> --request REQUEST_ID` hands it to you as a normal `?` question; herdr does the same, recording why, when the owner's pane closes or its agent exits (then for every later question too), when its agent hits a usage or credit limit or is blocked on its own question to you (also for questions asked until it works again), when its agent ends its turn with the question unanswered (acknowledging is not answering), and when herdr starts. No timer decides it: a coordinator hung while shown as working keeps its questions quiet. Once escalated a question stays loud; either side may answer it, and the first answer wins. After handling it (answering or escalating the question, reviewing the turn or the ended worker), the owner runs `worker ack <id> <seq>` with the `seq` the wait or the list returned; an ack only grows, and repeating one changes nothing. A `worker stop` or `worker kill` run by the owner's pane acknowledges the exit it causes, so an end the owner asked for is no obligation; an exit nobody asked for, or one another pane caused, still is. `worker prompt` returns `turn_seq`, the `seq` of the message it sent; `worker interrupt --turn SEQ` interrupts only that turn and is refused once it has ended. `worker stop` sends SIGTERM and returns; the worker turns `exited` when its process ends, and until then its status carries `stop_requested_ms`. It never escalates; `worker kill` does, and also ends the tool processes the worker left behind, but only those whose session leader is still the process herdr recorded. For an `exited` or `lost` worker it signals nothing without `--force` and prints what it would kill. `worker answer` answers the question `--request` names (its `request_id` from `worker status` or the `?` list, which prints the command); `--request` is required, and an id that is no longer pending is refused with what ended it. The answer is `allow` or `deny` for a tool approval (`--message` goes to the model with a denial), or one choice per `AskUserQuestion` question, each an option's label, its 1-based number or free text, with several options of a multi-select question separated by commas. A question can also be answered in herdr: a click on it in the `?` list, or on the line of a worker that waits on one, opens a dialog with the worker's task, its owner and why the question was escalated to you, and the whole command (newlines kept, scrolled, never cut) or the question's options as buttons. Its buttons are Allow once, Deny (with an optional message for the model), View log, Stop worker (after a confirmation; the question is denied and the worker stopped) and, while the owner's pane is open, Open owner. Allow and Deny wait until the whole command has arrived from the server, and Enter presses only a button chosen with Tab, so no key answers by default. When the question is answered elsewhere or the worker exits while the dialog is open, it says so and its buttons stop working. With several questions waiting it shows `1 of 3`, and after an answer the next one opens. `worker log` prints the worker's journal as text (the assistant's words, tool calls and results, decisions, each turn's result); `--follow` keeps printing new events until `q`, Esc or Ctrl-C, as the sidebar's log view does. `worker take-over` interrupts the worker's turn, waits for its `result`, stops it, waits for its exit and then opens a tab in its space and directory running `claude --resume <session>`; Claude asks there whether to trust the directory. It is refused while a question waits on you. The tab carries the takeover's id in `HERDR_TAKEOVER_ID` and in its title, so when herdr restarts before recording the tab, it finds the tab by that id (or by a process running `claude --resume <session>` in one of its panes) and adopts it. When it finds none, `worker status` shows `takeover_unfinished` and `take-over` is refused: the earlier attempt may have opened a tab you did not see, and a second tab on the same session forks its transcript. `--force` retries it anyway.

`worker start`, `prompt`, `interrupt`, `stop`, `kill` and `answer` take `--command-id ID`, a client's id for that one command: it runs once per id, a repeat returns the first outcome (the same reply, or the same refusal) without doing it again, a repeated `start` returns the worker that id started, and the same id with another command or other arguments is refused with `worker_command_conflict`. A coordinator derives the id from its task (for a start, the TODO item and branch), so a retry after a lost reply cannot start a second worker or send a second answer.

A headless worker starts with all hooks off (`disableAllHooks`), so the PreToolUse hooks in your Claude Code settings do not run in it. To run checks of that kind in every worker, list them in the herdr config:

```toml
[workers]
pre_tool_checks = [["python3", "~/.claude/hooks/delay-check.py"]]
```

Each check is an argv list (`~` is expanded in every argument; no shell). Before each Bash, Write, Edit and MultiEdit call herdr runs the checks in the worker's directory, outside its sandbox, one after the other, with Claude Code's PreToolUse hook input as JSON on stdin (`tool_name`, `tool_input`, `session_id`, `cwd` ...) and `CLAUDE_PROJECT_DIR` set, as Claude Code runs a command hook. A check denies the call by exiting 0 with `{"hookSpecificOutput": {"hookEventName": "PreToolUse", "permissionDecision": "deny", "permissionDecisionReason": "..."}}` on stdout (or the older `{"decision": "block", "reason": "..."}`), or by exiting 2 with the reason on stderr: the worker's tool call is refused and the model sees the reason. The first denial wins and later checks do not run. Anything else is no objection; an `allow` or `updatedInput` is not passed on, so herdr's worker policy still decides the call. Herdr registers the checks as a callback hook of its own when the worker starts (the CLI's `initialize` request), so they run although the user's hooks stay off, and also for the Bash commands the sandbox lets run without asking. Each verdict is a `pre_tool_check` event in the worker's journal, and `worker log` shows a denial. A check that cannot start, exits with another code or by a signal, or prints broken JSON fails open: the call goes on and the failure is a `pre_tool_check_failed` event, shown in `worker log`. Herdr sets no time limit on a check; when the CLI gives up on the hook (its own hook timeout, or the turn ends) it cancels the request, and herdr kills the check and reports that the same way. The config is read when a worker starts: a change applies to the next worker, and a worker keeps its checks across a server restart or handoff. A config that cannot be read starts the worker without checks and reports why.

A headless worker may not wait in the background: nothing wakes it after its turn ends, so work it left running would sit unfinished. Herdr denies, in every worker, a Bash call or an agent (`Agent`) that runs in the background (`run_in_background`, which an agent defaults to) and every `Monitor`, `ScheduleWakeup` and `CronCreate` call, with the reason "you are a headless worker: nothing wakes you after your turn ends, so run it in the foreground", so the model runs it again in the foreground. The rule runs in the same callback hook as the pre-tool checks, before them and whether or not any is configured, so it also covers the Bash commands the sandbox lets run without asking; each denial is a `permission` event in the worker's journal.

A live handoff (`herdr server live-handoff`, which `herdr update --handoff` also sends) does not carry the workers' pipes. A worker whose broker owns them (below; `survives_handoff` in its status) survives it, in a turn or not: once the handoff succeeded the old server lets go of it, and the new server re-attaches as after a restart. For the other workers (started by a build without the broker, or on Windows) it is refused while any one's process is alive, in a turn or idle between turns, with a message naming them; end them first with `herdr worker stop <id>` (safe for one idle between turns) and `herdr worker wait <id> --exit`, or hand off anyway with `--force`, which sends them SIGTERM. The server never waits for them inside the handoff. `worker drain start` readies an install without ending anyone's turn: the server admits no new turns (`worker prompt` and `worker start` are refused with `workers_draining`, naming `--reason`), while running turns go on and their questions can still be answered; it prints the workers still in a turn. `worker drain status` only reports, and `worker drain cancel` admits turns again. The drain lives in the server's memory, so the server a handoff starts does not drain. `worker wait-drained` blocks until no worker is in a turn, woken by their turn-end events with no timeout, printing each turn as it ends; it exits 1 when the drain it saw is cancelled first. `scripts/herdr_live.sh install` (and `rollback`) drains first: when a worker is in a turn it names it, says how to give up (`herdr worker drain cancel`, or Ctrl-C, which also cancels the drain) and waits with `worker wait-drained`; then it stops the idle workers, waits for their exits and hands off. With a running build that has no drain it refuses while a worker is in a turn, and `--force` skips the drain and the stops. The server that runs a worker holds a lock on `<id>.lock` beside its journal, so a server started by a handoff marks a worker `lost` only once the old server has let go of it, and an exit journaled later replaces `lost`. A worker whose server ended while it was between turns keeps its last turn's state, with `end_note` "ended by a server restart", instead of `lost`. On Unix a new worker runs under a broker process that owns its pipes and outlives the server; the broker numbers each line of the worker's output and syncs it to a spool (`<id>.spool` beside the journal) before handing it on, so a server that starts while the worker runs re-attaches and stores the lines written while no server read them, each once. A broker that cannot write its spool ends the worker, which is then shown degraded. A re-attach counts as whole only when the broker replays every line after the last one the store holds; when that cannot be proven (a broker of an older build without a spool, a spool that starts after that line, a missing, damaged or cut spool), the worker is shown degraded with the reason, nothing is inferred for it, and `worker prompt` and the takeover are refused with `worker_continuity_gap`. Every line a server writes to a brokered worker's input carries an id (the command's `--command-id`, or for an answer its question's request id); the broker writes a line to the worker once and journals it as `input_written`, and a line whose id it already wrote is only acknowledged (`again`). So after a restart or a handoff the new server sends again each answer stored but not confirmed sent, and settles it as answered, without the worker reading it twice; a permission request the old server stored but neither asked nor answered is decided again, and its question asked, by the new one.

A repository has one coordinator at a time (see `coordinator.*` in the socket API):

```bash
herdr coordinator start [--repo DIR]
herdr coordinator end [--reason TEXT] [--id COORDINATOR_ID]
herdr coordinator status [--repo DIR]
herdr coordinator handoff --to PANE [--id COORDINATOR_ID]
```

`coordinator start` claims the coordination of the repository of `--repo` (default: the caller pane's directory) for the caller's pane (`HERDR_PANE_ID`): a tenure with an id of its own (`c-...`). It is refused with `coordinator_active`, naming the other tenure and its pane, while another pane coordinates that repository. `herdr tab role <tab> coordinator` does the same for the tab's focused pane, and the tab's `♛` follows the tenure: `coordinator end` (this pane's tenure, or `--id`'s) or `herdr tab role <tab> none` ends it, and so does closing its pane or exiting its agent. `coordinator status` lists the active tenures, each with the TODO item its `herdr todo run` works on until the run ends. Workers and runs started from a coordinator's pane carry its tenure's id (`owner_coordinator_id`) and belong to the tenure, not to the pane: when the coordinator's agent session comes back in another pane (`claude --resume`), the tenure, its workers, their obligations and its runs move there, and another session in the old pane inherits none of them. `coordinator handoff --to PANE` passes the coordination on: this pane's tenure (or `--id`'s) ends `handed_off`, and the next one, one epoch on, starts in `PANE` with the item, workers and runs.

In a tab with the role `coordinator`, the Claude integration's `PreToolUse` hook holds the agent to what a coordinator does itself. It allows `herdr todo`, `worker`, `history`, `coordinator`, `report` and `reports`; `herdr agent read`, `list`, `get`, `explain`, `awaiting-reply` and `set-task`; `herdr-job wait`, `list`, `log`, `watch`, and `run` with an allowed command; read-only git (`status`, `log`, `diff`, `show`, `fetch`, `rev-parse`, `branch --list`, `ls-files`, without options that write a file or run a program); `git commit -- TODO.md DECISIONS.md` (by path, those files only); `python3 scripts/todo_edit.py`; `cat`, `head`, `tail`, `grep`, `rg`, `sed -n` (printing lines), `jq`, `ls`, `wc`, `date`, `df` and `du`; the consult helpers (`~/.claude/skills/*/ask_*`, `consult.py`); output redirected only to `/dev/null` or the session's scratchpad. Of the other tools it allows those that read or ask (`Read`, `Grep`, `Glob`, `AskUserQuestion`, `Skill`, `ToolSearch`, `TodoWrite`, and reading or stopping its own background shells), and `Write` and `Edit` only under the session's scratchpad (Claude's `<tmp>/claude-<uid>/<project>/<session>/scratchpad/`). Everything else is denied with the reason and the allowed path: builds, installs, pushes and cherry-picks happen in `herdr todo run`, code goes to a worker, `TODO.md` and `DECISIONS.md` are edited with `scripts/todo_edit.py`, work goes to a worker rather than a subagent. A compound command (`;`, `&&`, `||`, `|`, newlines, `$(...)`) runs only when every part is allowed, a quoted heredoc's body is data, and a command the hook cannot read for certain (backticks, subshells, brace or arithmetic expansion, a variable as the command or in a git argument, environment assignments, `&`) is denied. An exception is one Bash command that carries `# herdr-override: <reason>`: herdr records it (`coordinator.record_override`) and notifies you, and `herdr history overrides` lists it; when herdr cannot record it, the command is denied, so an exception is never silent. The hook asks herdr nothing for an allowed call; for any other it asks the tab's role, and outside a coordinator tab, or when herdr cannot tell, it does nothing.

What happens to a call the allowlist refuses in a coordinator tab is set in the herdr config:

```toml
[coordinator]
allowlist = "shadow" # or "enforce", "off"
```

In `shadow` mode, the default, nothing is denied: the call runs, and herdr records it as a would-deny (the tool, the command or file path, the allowlist's reason, the pane, the coordinator's tenure, item and repository, and the time) in the worker store, beside the overrides; `herdr history overrides --would-deny` counts them per command shape and lists them, so you can decide from real use whether to enforce the allowlist. In `enforce` mode the call is denied as described above, and `# herdr-override: <reason>` is the exception. In `off` mode the call runs and nothing is recorded. The hook asks herdr the mode for each refused call (`coordinator.allowlist_refusal`), so a change applies to the next call; a herdr that cannot answer (one older than this setting, or one that does not reply) gets the call denied, as in `enforce` mode. A headless item coordinator (`herdr todo next`) always enforces the allowlist.

A coordinator drives one TODO item at a time with `herdr todo` (see `todo.*` in the socket API), so the execution steps are herdr's, not the model's:

```bash
herdr todo run <item-id> --task FILE --message SUBJECT --paths GLOB... --check NAME... [--ignore-usage] [--auto-review] [--auto-answer]
herdr todo run <item-id> --draft [--ignore-usage]
herdr todo wait <run-id> [--after EVENT_ID]
herdr todo resume <run-id> --event EVENT_ID --action approve|retry|answer|verify|force-stop|retry-install|skip-install|retry-todo|skip-todo|retry-push|abort [--task FILE [--ignore-usage]] [--note FILE | --keep-open | --close FILE (--next ITEM --next-task FILE --next-message SUBJECT --next-paths GLOB... [--next-check NAME...] | --stop-reason TEXT)] [--request REQUEST_ID] [--message TEXT] [allow|deny|<choice>...]
herdr todo status <run-id>
herdr todo review <run-id> [--attempt N] [--diff] [--json]
herdr todo runs [--repo DIR] [--commit SHA]
```

`todo run` first checks everything the run needs and refuses with `todo_preflight_failed`, starting nothing, when one fails: the item's id is in the repository's `TODO.md`, the task file is not empty, SUBJECT is a lowercase conventional commit subject (`feat: ...`, `fix(scope): ...`, one line, the description not starting with a capital), each GLOB is a relative git glob (no absolute path, `..` or pathspec magic), each NAME is a check registered in the repository's `.herdr/checks.toml` (named once), the disk has at least its `[preflight] min_free_gib` free (15 GiB by default, the limit of `just guard`), and the folder slot `../herdr-worktrees/worker` has no running worker and no uncommitted change. A repository has one run in progress at a time (`todo_run_active` names it). The run (`r-` and 8 characters) records `master`'s commit as its base, starts a headless worker in the folder slot on the new branch `todo/<item-id>-<run-id>-<attempt>` from it (so a later run of the same item never meets an earlier run's branch), with FILE's text as its task followed by the run's contract (run everything in the foreground, the exact SUBJECT as the one commit's message with no body and no trailers, the GLOBs it may touch, each check the verify runs by name and argv with the order to run every one it can in its sandbox before its last line and report each result or the sandbox error that stopped it, that advertised client methods keep their v1 shape, and its last line `WORKER-DONE <sha> | <summary>` or `WORKER-BLOCKED <reason>`), `--item` set, the caller's pane and agent session as its owner (bound to that pane's coordination tenure, so its questions, obligations and escalation work as for a worker started with `worker start`) and the caller's workspace as its space, and then waits on the worker. Each later attempt's worker gets the same owner and space. A question the worker policy leaves (a tool approval, an `AskUserQuestion`) becomes a `question` event; the end of the worker's turn, or of the worker, a `review` event with the branch's commits, diff stat and the worker's last reply; the worker's events up to there stay the owner pane's obligation (`worker obligations`) until `todo resume` answers the event, which acknowledges them. `todo wait` blocks until the run waits on an event after `--after` (or has ended: then its last event) and prints it with its `event_id`, the actions it takes and its evidence. When the server goes away while it waits (the live handoff of an install), it waits for the server socket to accept again, checks the new server's protocol and goes on waiting on the same run after the same event; it gives up only when the new server does not know the run (`todo_run_not_found`). `todo resume` answers that event, naming it with `--event`: any other id is refused with `todo_event_stale`. Only the run's owner pane resumes it: a resume from another pane, or from outside a pane, is refused with `run_owned_elsewhere`, naming the owner, while that pane is there. Once the owner's pane closed or its agent exited (as herdr's events report it, never a timer), a resume from another pane takes the run over: its pane, agent session and workspace own the run and its later workers from then on, recorded as a `run_owner_taken` event with the previous owner and the cause. `answer` sends the worker the answer (`allow`, `deny` or one choice per question); `approve` stops the worker (as its owner) and waits for its exit, then verifies its commit like `worker verify`, with each registered check as a command in the order given (every one must pass; each `command` check carries its `name`), plus the registered `tests` check when the run does not name it and the commit's diff touches `src/api/` or `tests/fixtures/`, so an API change is verified with the frozen client contract tests (recorded as a `run_check_added` event; the contract names it too), and cherry-picks it onto `master` in the repository's checkout; `retry` stops the worker and starts the next attempt on a new branch from the same base, with `--task FILE`'s text as the review of this attempt (below). A failed or unavailable verify is a `verify_failed` event with each check's evidence, which takes `retry` or `verify` (the verify again, for instance after a check was unavailable). A run has at most 3 attempts: a retry after the third stops the worker and blocks the run. After the stop the run waits for the worker's exit event with no deadline. When `todo status` is asked while the stop is sent and the worker's process is still alive (it ignores SIGTERM, for instance), the run raises a `still_alive` event, which takes `force-stop` (SIGKILL, sent as the run's owner) and which a waiting `todo wait` then returns; no clock raises it, `todo wait` alone does not, and herdr never kills the worker on its own. The run goes on by itself when the worker exits first. The cherry-pick is refused, blocking the run, when the checkout is not on `master`, has uncommitted changes or a cherry-pick in progress, or its `master` no longer contains the base; a conflict is aborted and blocks it too. Nothing is rebased.

A run keeps each attempt: its worker, branch, base, task, the previous attempt and commit it started from, its commit, the coordinator's decision on it (the event, `approve`, `retry` or `abort`, and a retry's text) and its latest verdict, one row per attempt in herdr's worker store, while the run itself points at the current one. On `retry` the driver carries the attempt on: before the next worker starts, it cherry-picks this attempt's commit (its branch's tip, when it has commits since the base) onto the base without a worktree, with the same author, dates and message, and starts the next attempt's branch from it (a `run_carried` event); the next attempt's task is this attempt's with `Review of attempt N:` and the retry's text appended, and its worker is told to amend that commit, so the branch still has exactly one commit when it is verified. A commit that does not cherry-pick onto the base (an attempt with several commits whose last depends on the others) is a `retry_conflict` event naming the conflict, which takes `retry` (without `--task`: the attempt then starts from the base, with the same review, and its worker is told that its branch lacks the previous commit) or `abort`. `approve` is bound to what the event showed: the attempt records the last commit of the `review` event's `commits` and the run's base, and before the cherry-pick the driver compares the branch's tip with them; a branch that moved since (amended in the folder slot, say) is not landed but raises a new `review` event, whose `error` names the approved commit and the tip, and which the coordinator approves, retries or aborts as any review. When the run lands the commit it adds the trailers `Herdr-Item: <item-id>` and `Herdr-Run: <run-id>/<attempt>` to the landed commit's message (the worker's own commit stays subject-only, as the verify requires), and records the landing (the landed sha, the run, the attempt, the item, the worker's commit and the time) with its `run_picked` event. `herdr todo runs --commit SHA` finds the run that landed a commit (SHA, at least 7 hex digits, is the landed commit or the worker's): in the store's landings, else by the commit's trailers in the history of `--repo DIR` (default: the current directory), so a commit whose sha the upstream rebase changed is still found. It prints the landing (`source` `store` or `trailers`, and the attempt's worker, whose log is the run's transcript); a commit no run landed is refused with `todo_run_not_found`. Runs recorded before attempts were kept get their attempts and landings from their stored events when herdr opens the store; their landed commits have no trailers.

`herdr todo review <run-id>` prints in one view what the coordinator reviews of an attempt (`--attempt N`, default the run's current one): the task the worker got, with the run's contract appended (its first prompt, from its journal); its last reply; the questions it asked with their answers; the tool calls that failed or were denied (by the policy, a pre-tool check or the CLI's permission mode); `git diff --stat base commit` in the repository, with `--diff` the full diff too; the verify's checks with their outcome and evidence; the coordinator's decision and a retry's review; and, once approved, the `(commit, base)` the approval is bound to and the commit it landed as. The attempt's commit is the one the decision saw, else the verify's head, else its branch's tip. It joins the run's attempt row, the worker's journal and git; nothing else is stored for it. `--json` prints the server's reply (`todo.review`). In the Items dropdown, an attempt of an item's timeline opens the same view, fetched when it is clicked, with a row that opens the worker's log; Back returns to the timeline.

Last, preflight asks the usage gate, since the run starts a headless Claude worker. It reads Claude's usage from the provider at that moment, in that call, with the same fetch the usage poller makes (no timer reads usage, and the gate never uses the poller's cached reading, a reading's age or a window's `resets_at`), and refuses with `usage_gate`, starting nothing, when any Claude window is 90% or more used, or when the read fails (no login, an expired login, the network, a rate limit of Claude's usage endpoint): unknown usage refuses too. The message names each window that refuses with its value, or the read's failure. The read's outcome also goes into the poller's shared cache, so the footer shows the new reading and a rate limit backs the poller off. A refusal closes the repository's gate, and a closed gate admits again only once Claude's usage, read when a run is asked for, shows every window below 80%. The gate's state is kept with the repository's runs in the worker store, so a server restart keeps it closed. `todo resume --action retry` asks the same gate before it starts the next attempt; its refusal leaves the run waiting on the same event. `--ignore-usage` (with `todo run`, or with `--action retry`), given on the user's word, starts anyway; the run's `run_created` or `run_resumed` event records it with the gate's decision (`usage_gate`), and an override leaves the gate's state as it was. A run already started is never stopped or paused when a window crosses 90%. The coordinator reports a `usage_gate` refusal to the user and stops there; it does not poll.

With `--auto-review` the server reviews the run's `review` events itself instead of handing them to the coordinator. For each one the driver first stops the attempt's worker (waiting for its exit event) and runs the verify on the event's commit with the registered checks, read-only, recorded as a `run_review_verified` event, so the model judges real results. Then it makes one bounded, stateless call, `claude -p` with structured JSON output (`--json-schema`), no tools, no session kept, no MCP servers, hooks or project instructions, the user's normal Claude login and the server's environment without `HERDR_*`, run by the server, not in a worker sandbox. Its input is the item's text, the attempt's task, the commit subject and paths, the worker's last reply, the diff of the event's commit against the run's base (cut at 200,000 bytes) and the registered checks with that verify's outcome and evidence. It must answer `approve` (an optional note), `retry` (the review text) or `escalate` (a question for the user with 2 to 4 options). The server checks the answer against the schema and against the run's state and applies it at once: `approve` as `todo resume --action approve` would, bound to the event's last commit and the run's base; that approval takes the verdict of the verify before the review instead of running the checks again (`run_verified` with `reused: true`) unless the branch moved or a check was added, and an approval of a commit whose verify failed is escalated instead; `retry` as `--action retry` with the review text, behind the same usage gate; `escalate`, an action the run cannot take (an approval without a commit or of a failed verify, a retry after the last attempt or one the usage gate refuses) and a call that failed or answered invalid output twice (it is made once more after the first failure) raise a new `review` event whose `error` holds the question and its options, and send the user a notification. The escalation also enters the user's `?` list as a question of the run's worker naming the run, the item and the question, with the options; its answer dialog answers it: an option (or free text) raises a new `review` event carrying the answer (`user_answer`), which the server reviews again with the answer in the model's input, and Deny takes it off the list (`run_escalation_declined`) and leaves the event to the coordinator. The coordinator answers the escalated event as any review, which takes it off the list, and the server does not review it again. Each call is recorded as a `run_review_call` event, and the decision, with its id (`d-...`), the input's SHA-256, the output, the model and the verify's verdict, as a `run_review_decision` event before it is applied (`run_auto_reviewed`), so a server that ends in between applies the recorded decision when it starts instead of asking again, and a call recorded for the same input is not made again. `todo wait` does not return a `review` event the server is still deciding; `todo resume` answers it all the same, and when it comes first the model's decision is recorded as superseded (`run_review_superseded`). The call's process exit is what the driver waits for, with no deadline. `todo status` shows `auto_review: true`, and `todo run` exits 1 with a message when a server that predates `--auto-review` started the run without it. A run a close starts with `--next` is reviewed the same way.

With `--auto-answer` the server answers the questions the worker policy leaves (the `question` events) the same way. For each pending question the driver makes one such call with the item, the task, the commit subject and paths, the request (the tool, its whole input, why the policy left it) and the run's policy; it must answer `allow`, `deny` (a message for the worker), `answer` (one answer per question of an `AskUserQuestion`: an option's label or free text) or `escalate` (a question with 2 to 4 options). The actions offered depend on the request, in the schema the call gets and in the server's check of the output: an `AskUserQuestion` takes `answer`, `deny` or `escalate`; a request of `WebFetch` or `WebSearch` takes `allow`, `deny` or `escalate`; a request herdr's policy leaves to the user (one the CLI's classifier escalated, a Bash command naming a path outside the worker's folders, any other tool) may only be escalated, and the server escalates it without a call. The answer goes to the worker as `todo resume --action answer` would send it, with a command id derived from the decision, and the run goes back to its attention step (`run_auto_answered`). An escalation hands the worker's own question to the user (it leaves the coordinator's quiet list for the user's `?` list, its cause naming the run, the item, the decision, the model's question and options), raises a new `question` event with the question for the coordinator and sends a notification; once the question is answered (from the `?` list or by the coordinator), the run goes on. A call that fails or answers invalid output twice is escalated. Calls and decisions are recorded as `run_answer_call` and `run_answer_decision` events before the answer is sent, and reused after a restart. `todo status` shows `auto_answer: true`; a server that predates `--auto-answer` makes `todo run` exit 1 as above, and a run a close starts with `--next` answers the same way.

With `--draft` (`todo.draft_run`) the server writes the task, SUBJECT, the GLOBs and the check NAMEs itself, so the run takes only the item's id (`--task`, `--message`, `--paths` and `--check` are refused; `--auto-review` and `--auto-answer` are implied). Preflight checks the rest first (the item in `TODO.md`, `.herdr/checks.toml`, the disk, the folder slot, the usage gate), and the run starts at its `draft` step: one bounded `claude -p` call, as for a review, with the item's text as the claim recorded it, the `DECISIONS.md` sections the item names (by their title or the item's id), the code, test and commit sections of `AGENTS.md` (both as the run's base has them), `.herdr/checks.toml` with its check names, `git log -20` of the base and the item's history. It must answer `draft` (the task text, the exact commit subject, the path globs and the check names, which the schema limits to the registered ones) or `escalate` (a question with 2 to 4 options, for an item that needs the user first). The server checks a draft as `todo run` checks those flags: a lowercase conventional subject, relative globs inside the repository (no absolute path, no `..`, no `:`), at least one registered check named once. A refused draft or a failed call is asked once more, its input naming why the earlier answer was refused (`rejected_drafts`); a second failure is escalated. Calls and decisions are recorded as `run_draft_call` and `run_draft_decision` events before the draft is applied, and reused after a restart. A valid draft is written to the run (`run_drafted`), which starts its worker exactly as `todo run` with those flags would. An escalation is a `draft` event the run waits on (its error holds the question and its options), a notification, and an entry in the user's `?` list under the run's id (the run has no worker yet); the user's answer there, or `todo resume --action retry --task FILE` with the answer, records it (`run_draft_answer`) and drafts again with every answer so far; `abort` ends the run. `todo status` shows `drafted: true`, and `todo review` shows the draft (its decision, model, subject, paths and checks) after the task.

While a decision step cannot go on (the worker store refuses a write, a worker cannot be stopped), the run is not hidden: `todo wait`, `todo status` and `todo runs` show it `blocked` with the error, the `blocked` event named by the event the run waits on (a wait after it waits for the run to go on), and the driver takes the step again at the next write the worker store announces; the store keeps the run waiting on its event, which `todo resume` still answers.

After the cherry-pick the run goes on by itself. It installs `master` with the `[install]` command of `.herdr/checks.toml` (as preflight read it), run in the repository's checkout with the coordinator's environment, its output in `run-<run-id>-install.log` next to the worker store, and records as `installed_build` the first line its `build_id` command prints; without `[install]` the step is skipped. A failed install, or one without the coordinator's environment, is an `install_failed` event with the log's last lines, which takes `retry-install`, `skip-install` or `abort`. Then, when the approval gave `--note FILE`, it appends FILE's lines (indented, blank lines dropped) to the item in `TODO.md` with `scripts/todo_edit.py append-to`; with `--close FILE` it removes the item and adds FILE to `DECISIONS.md` as a section (`todo_edit.py add-section`; FILE's first line is the section's title when it starts with `#`, the item's title otherwise). The edit is made on copies of `HEAD`'s files, written over the checkout's only when those files have no uncommitted changes, and committed by path as `docs(todo): note on <item-id>` or `docs(todo): close <item-id>` (`todo_commit`). A file with another session's uncommitted changes, a checkout not on `master` or a refused edit is a `todo_failed` event, which takes `retry-todo`, `skip-todo` or `abort`. Then it pushes `master` to `origin` with the coordinator's environment, only as a fast-forward: when `origin`'s `master` is not an ancestor of the local one, or the push fails, it is a `push_failed` event, which takes `retry-push` or `abort`, and nothing is ever forced; a repository without `origin` skips the push. Last, it deletes the run's attempt branches whose changes `master` has (`git cherry`), except one a worktree has checked out (the folder slot's), which it keeps in `kept_branches` for a later run's cleanup: the next run, before its worker starts, detaches the folder slot when it is still on such a branch and deletes it (a `run_slot_released` event); a rejected attempt's branch stays. A run that ends is `done` (its `picked` commit is on `master`, with `installed_build`, `todo_commit` and `pushed` as far as they ran), `blocked` (its `error` says why) or `aborted`; each is a last event. A closing approval also carries what follows the close, so no coordinator ends a closed item without saying what comes next: `--close` is refused unless it comes with `--next ITEM` or `--stop-reason TEXT` (not both; neither comes without `--close`), except in queue mode (`todo queue`, below), where it takes neither. With `--next`, once the run is `done` the driver starts ITEM's run itself, as `todo run` would with `--next-task`, `--next-message` and `--next-paths` (all required with `--next`) and the closed run's checks unless `--next-check` names others, in the same repository and owned by the closed run's owner. It records the intent before the start (`run_next_intent`) and the started run after it (`run_next_started`, and `next_run_id` in `todo status`); a server that ends in between starts it when it starts, or finds the run that start already made. A start the next run's preflight or usage gate refuses is a `next_refused` event on the done run naming the refusal (`next_refusal` in `todo status`), which `todo wait` returns as the run's last event; the item is then started by hand. With `--stop-reason`, TEXT goes into the item's history (`stopped`) with the run's `done` event and to the user as a notification. `abort` answers any event the run waits on, or the `blocked` event of a blocked run (which takes only `abort`; any other id is refused with `todo_event_stale`): the run stops its worker when it still runs, as its owner, waits for the worker's exit event (a `still_alive` event and `force-stop` apply as after `approve`), and ends `aborted`. Its `error` is the reason, with `--message TEXT` appended, and names what it leaves as it is: each attempt's branch with its commits since the base (listed in the `aborted` event's `commits`) and a commit already picked onto `master`. Nothing is deleted or reverted. A run at its abort step no longer counts as the repository's run in progress; the folder slot's busy check keeps a new run out until the worker exited.

`.herdr/checks.toml` maps each check's name to a program and its arguments (and `[install]` the install's), run as they are in the worker's folder (the install in the repository's checkout) with the environment of the shell that ran `todo run` or, after it, the last `todo resume` (without `HERDR_*`; every resume sends it again, and the server keeps it in memory only, never stored, since it may hold credentials), never through a shell. A live handoff carries these environments to the new server inside its handoff message over the local socket between the two servers, never on disk, so a run's install, push and checks go on after `just clean-install` hands off. A check without it (after a restart, a resume that sent none, or a remote caller) is `unavailable`, never run in the server's environment; `todo resume --action verify` from the coordinator's shell sends it and verifies again:

```toml
[checks]
workers = ["cargo", "nextest", "run", "-E", "test(/workers::/)"]
windows-lint = ["python3", "scripts/windows_cross.py", "lint"]

[preflight]
min_free_gib = 15

[install]
command = ["just", "clean-install", "TODO.md"]
build_id = ["herdr", "--build-commit"]
```

`todo run` keeps the checks' argv as preflight read them from the repository's checkout, so the worker's commit cannot change its own checks. Each step is recorded in herdr's worker store as an intent before its side effect and its result after it (the run's `run_*` events, with its row, in one transaction), and a herdr server that starts drives every run in progress again from its step: the start and the stop carry command ids derived from the run, so a repeated one returns the first outcome; the wait on the worker starts after the events the run already handled; a cherry-pick whose commit `master` already has is not made again; an install whose `build_id` already names `master`'s commit (a clean build of it) is not run again; a TODO commit `master` already has is not made again; and a push is not repeated when `origin`'s `master` already contains the local one. One server drives a run at a time: its driver holds the run's lock file next to the worker store (`run-<run-id>.lock`). After a live handoff the old server's drivers let go of their runs at their next step or liveness check, without blocking them, and the new server's driver waits for the lock (a `run_lock_wait` event) until the old server let go or ended; the operating system releases the lock then, so no timer decides it.

Instead of one long-lived coordinator session, herdr can start a fresh headless coordinator for each item, keeping the coordinator's judgement in a model and its state only in files:

```bash
herdr todo next [--repo DIR] [--continue]
herdr todo stop [--repo DIR]
```

`todo next` starts an item coordinator for the first open item of the `## Next, in order` section of the repository's `TODO.md` (of `--repo DIR`, default the current directory): a headless Claude worker in the repository's checkout, owned by the caller's pane (`HERDR_PANE_ID`), under a coordination tenure of its own that no pane binds (`coordinator status` shows it `headless`, with its worker). Its prompt, built by herdr, holds the item's id and text, what to read first (`TODO.md`, `DECISIONS.md`, `AGENTS.md`, `git log -20`, `herdr history --item`, `history reconcile`, `.herdr/checks.toml`), the driver commands it may use (`todo run`, `wait`, `resume`, `review`, `status`, `scripts/todo_edit.py` for its own item) and its contract: it checks the item, writes the worker's task, starts the run, reviews and answers each event, closes the item with `--close` (or notes it), and ends with its last line `COORDINATOR-DONE <item> | <summary>`, `COORDINATOR-ESCALATED <question>` or `COORDINATOR-BLOCKED <why>`. A question it cannot decide goes to you as a question in the `?` list at once (not quietly to the pane that started it); it never guesses. It runs under the coordinator allowlist above, as herdr's first pre-tool check, in its headless mode: a refused command is denied, and there is no `# herdr-override:` (it asks you instead). Its Bash sandbox may reach the herdr server's socket, so its `herdr todo ...` commands work, and it writes its task and decision files only in its own temp directory. The runs it claims belong to its tenure, and their checks, install and push run with the environment of the shell that ran `todo next` (kept in the server's memory only), not the coordinator's sandboxed one. `todo next` is refused while the repository has a run in progress (`todo_run_active`) or an active coordinator, of a pane or headless (`coordinator_active`), when the section has no open item (`todo_preflight_failed`), and when the usage gate of `todo run` refuses (`usage_gate`).

When the coordinator's turn ends, herdr stops it, and on its exit event ends its tenure (`item_done`, `item_escalated`, `item_blocked` or `item_failed`) and records the outcome in the item's history (`coordinator_started` and `coordinator_ended` records, see `history --item`). Herdr checks a reported `done` itself: a run of the repository still in progress, or the item still first in `Next, in order`, makes it `blocked`. With `--continue`, a coordinator whose item is done starts the next item's coordinator on that exit event (no timer), with the same owner, until the section is empty, an item escalates, is blocked or fails, or `todo stop` stops the chain; `todo stop` lets the running coordinator finish its item and starts no next one. An end that starts the next coordinator is acknowledged for you; any other stays an obligation of the owner pane (`worker obligations`) until it is acknowledged. A server that starts watches the item coordinators a previous one left and starts the next coordinator of a chain whose last item ended done just before it. The pane that runs `todo next` only talks with you, queues requests and starts or stops the chain.

In queue mode the server drives the queue itself, with no coordinator agent in the loop: the model is called only at the typed decision points of a `--draft` run (the task draft, the review, the worker's questions).

```bash
herdr todo queue on [--repo DIR]
herdr todo queue pause [--repo DIR] [--reason TEXT]
herdr todo queue status [--repo DIR]
```

`queue on` sets the repository's mode to `on` (kept in the worker store, so it survives restarts and handoffs) and evaluates the queue at once. While the mode is on, no run of the repository is in progress (a run at its abort step counts until it ended), no headless item coordinator runs and the usage gate admits, the server starts the top item of `## Next, in order` that is not blocked, as `todo run <item> --draft` would, owned by the pane that ran `queue on`; its checks, install and push use that shell's environment, kept in the server's memory only and carried by a live handoff. A server that started cold has none: instead of starting a run whose checks would be `unavailable`, the queue pauses with the reason "environment needed: run `herdr todo queue on` from your shell" and a notification, and `queue on` from a shell sends it again. `TODO.md` is read from `master` (`git show master:TODO.md`) each time, and items are taken by their ids. The queue looks again only on herdr's own events, never on a timer: a run of the repository ended (`done`, `blocked` or `aborted`), an event was answered (an escalation from the `?` list or `todo resume`), the server started, the mode was set, and, while the usage gate stops the queue, the usage poller published a new reading (the start then asks the provider itself, as every start does). An approval in queue mode closes its item: the queue run's own review's, and `todo resume --action approve` without `--note` or `--close` of a queue run or of any run while the queue is on. The item leaves `TODO.md` and `DECISIONS.md` gets a section titled by the item saying which run and commit landed it and who approved it (with the review's note), so the next evaluation starts the next item and the queue never runs an approved item again; `--keep-open` leaves the item open. While a queue run waits on an escalation, nothing else starts; the answer lets the run go on, and its end starts the next item. Each start claims the queue's fencing token in the transaction that creates the run, beside the one-run-per-repository index, so concurrent evaluations (or two servers of a live handoff) start one run. A server that starts first drives the runs in progress again, then settles the queue runs that ended while no server looked and starts the next item. An item the queue ran 2 times with the same text is blocked (shown with the reason in `queue status`, and a notification) until its text in `TODO.md` changes; 3 consecutive queue runs that ended `blocked` or `aborted` pause the queue with the reason and a notification (the circuit breaker); `queue on` clears that pause and the count. `queue pause` lets the run in progress finish and starts nothing more. In queue mode `todo resume --action approve --close FILE` takes neither `--next` nor `--stop-reason` (both are refused there): the queue starts the next item.

`queue status` prints the mode (`on`, `paused`), the status with its reason (`running`, `waiting_on_user` for a paused queue or a run that waits on `todo resume`, `escalation_pending`, `usage_gate`, `blocked`, `empty`), the run in progress and its item, the circuit breaker's count (`failures`) and the blocked items. A usage gate's refusal is looked at again at the next event, at the next reading the usage poller publishes, or with `queue on`.

Herdr's server records the life of each TODO item a run works on, so you can look through finished items afterwards (see `history.*` in the socket API):

```bash
herdr history [--repo DIR] [--json]
herdr history --item <item-id> [--repo DIR] [--json]
herdr history reconcile [--repo DIR] [--json]
herdr history overrides [--repo DIR] [--json]
herdr history overrides --would-deny [--repo DIR] [--json]
```

The records live in the worker store on this machine, outside the repository and never committed, one append-only row per event of an item's life, written in the transaction of the run event that causes it (or of the item coordinator's start and end): `claimed` when `todo run` starts a run (with the item's whole text in `TODO.md` at that moment and the ids of every item there), `noted` when a run's `--note` is committed (the note), `closed` when a run's `--close` is committed (the decision, the item's last text, and the follow-ups: the items in `TODO.md` after the close that were not there at the claim), `aborted` and `blocked` when the run ends so (the reason), `stopped` when a run closed with `--stop-reason` is done (the reason; it follows the close, which stays the item's last record in `history`), `coordinator_started` and `coordinator_ended` when a `todo next` item coordinator starts on the item and ends (its outcome and what it reported). A record names its tenure (`coordinator_id`) and its run and attempt by id and copies nothing of them. `history` lists the recorded items, the most recent first, each with its last record and title. `history --item` prints the item's timeline: each record, then each run with its status and TODO commit, and each attempt with its worker, verdict, the coordinator's decision, its commit and the commit it landed; an item without records is refused with `history_item_not_found`. `history reconcile`, meant for a coordinator's start, compares the repository's `TODO.md` (of `--repo DIR`, default the current directory) with the records and reports claims without an end (no note, close, abort or block of their run; a run still in progress is marked so) and items seen at a claim that left `TODO.md` without a `closed` record. It only reports; it never writes or drops a record. Runs started before the records existed have none. An item whose records hold no text (claimed before the records kept it) takes its title from `TODO.md` while it is still there, else it shows its id alone. `history overrides` lists the exceptions to a coordinator tab's command allowlist (of `--repo DIR`'s repository when given), oldest first: each command that carried `# herdr-override: <reason>` and ran, with its time, reason, pane, the coordinator's tenure and item, and the command. `history overrides --would-deny` lists what the allowlist would have denied in `shadow` mode (`[coordinator] allowlist`): first the count per command shape (the tool, and for Bash the program of the first command other than `cd` with its first argument that is not an option, such as `Bash: cargo build`), the most frequent first, with the latest time and reason, then each call, oldest first, with its time, pane, item, repository and command. Times are printed in local time; `--json` prints the server's reply.

Coordinators report herdr's own protocol problems themselves, into a durable queue in the worker store rather than into a session (see `report.*` in the socket API):

```bash
herdr report --kind KIND --summary TEXT [--evidence PATH] [--uncertain] [--command TEXT] [--json]
herdr report close <r-N> (--fix ITEM_OR_COMMIT | --not-reproducible)
herdr reports [--open | --all] [--json]
```

A problem is reportable when a herdr command, wait, sandbox or skill step did not give its promised outcome or a clear next step: a wait that ended without a verdict, an unexplained exit code, a headless worker blocked by the sandbox, a skill step written for one repository, an error that does not say the way out, or a coordinator mistake that unclear instructions caused. The test is whether another coordinator in another repository would hit it; a worker's expected turn, a worker's wrong answer and the repository's own bugs are not reportable. When unsure, add `--uncertain`; the herdr coordinator decides. `KIND` is a slug (lowercase letters, digits and `-`, at most 40) and `TEXT` one line of at most 500 bytes. `herdr report` records the repository (of the current directory), the pane (`HERDR_PANE_ID`) and its tenure, the agent session, the time and `--command` (the command the problem came from), and keeps the first 64 KiB of `--evidence PATH` in the worker directory's `reports/`, so a temporary file may go away. It fingerprints `KIND` with `TEXT` after replacing paths, numbers, commit hashes and ids (`w12`, `r-…`, `t-…`) with placeholders, and prints `report r-N, occurrence K`. The first occurrence of a fingerprint notifies the herdr repository's coordinator once: a notification naming the report, pointing at that coordinator's pane, or to you when no pane coordinates the herdr repository (the repository whose `Cargo.toml` names the package `herdr`). Later occurrences only add a row (session, repository, time, evidence) and notify no one. `herdr report close` works only from the pane that holds the herdr repository's coordination tenure, refused otherwise with `report_close_refused`; it names the TODO item (`t-…`) or commit that fixed the report, or `--not-reproducible`. A later occurrence of a closed report reopens it and notifies again, naming the closure it reopened. `herdr reports` lists the open reports (all with `--all`), the latest occurrence first, each with its occurrences.

When `herdr todo wait`, `herdr worker wait` or `herdr worker verify` ends in a protocol problem, it prints the matching `herdr report` command with the kind, the summary and the command filled in, on stderr: a `todo wait` that gave up after a server handoff (`todo-wait-gave-up`), a verify that could not run a check and so has no verdict (`verify-unavailable`), a worker the server lost (`worker-lost`), and herdr's worker policy asking about a headless worker's Bash command that names a path outside its directories, which the sandbox refuses (`worker-sandbox-refusal`).

## Usage per workspace

```bash
herdr usage --workspace [<id|number|label>] [--since <date>] [--json]
```

Prints, for every workspace (or only the one named by its id, its number or its label), the tokens its agent sessions used per model (input, output, prompt-cache writes and reads) and an estimated cost. The output says so: it is an estimate, not the provider's bill. The cost is herdr's per-model list prices (`src/usage/prices.rs`, with their date and source in `prices_as_of` and `price_source` of `--json`) times the tokens; subscriptions, discounts, batch or priority tiers, fast mode and long-context surcharges are ignored. Every price comes from that one dated source; models it does not list (OpenAI and other non-Anthropic models, and older Claude models such as Opus 4 or Haiku 3.5) get no price from memory: their tokens are listed under their model id with "no price", and the workspace is marked as having unpriced tokens; for pi sessions the cost pi wrote into its transcript is used instead.

Only sessions herdr still knows are counted: the current or last session of each open pane and the workers the server lists; sessions of closed panes, earlier sessions of a pane and workers the server no longer lists are missing. A workspace's sessions are those its panes run or last ran (the session each pane's agent integration reported) and those of the headless workers its panes own; a worker whose owner pane is gone counts in the space it was started in. Each session counts once by its id, even when it was resumed in several panes or tabs, under the first space it was seen in (the others are listed as `also_in_workspaces`), and each Claude response counts once by its message and request ids, also when a resumed session copied it into a new transcript. Herdr reads the transcripts the agents write: Claude Code (`$CLAUDE_CONFIG_DIR` or `~/.claude`, `projects/*/<session>.jsonl` and its subagents), Codex (`$CODEX_HOME` or `~/.codex`, `sessions/**/rollout-*-<session>.jsonl`) and pi (the session file it reports). Sessions of other agents are listed without tokens. `--since` counts only entries from that date (`YYYY-MM-DD`, from local midnight, as herdr's other times are local) or RFC 3339 time on; the report prints the start in local time. The transcripts are read by the CLI when you run the command, never in the background; the server only lists the workspaces, panes and workers.

## Direct terminal attach

```bash
herdr terminal attach <terminal_id> [--takeover]
herdr terminal session control <target> [--takeover] [--cols N] [--rows N]
herdr terminal session observe <target> [--cols N] [--rows N]
herdr terminal title set <title>
herdr terminal title clear
```

Detach from direct attach with `ctrl+b q`. Send literal `ctrl+b` with `ctrl+b ctrl+b`.
`terminal session control` opens a writable live terminal stream for a pane,
terminal, or agent target. It prints the same newline-delimited
`terminal.frame` and `terminal.closed` records as observe mode. It reads
newline-delimited JSON commands on stdin: `terminal.input`, `terminal.resize`,
`terminal.scroll`, `terminal.mouse`, and `terminal.release`. One controller can
own a terminal at a time; use `--takeover` to replace it.
`terminal.mouse` sends one mouse event at a zero-based cell of the controller's
viewport, for example
`{"type":"terminal.mouse","action":"down","button":"left","column":12,"row":5}`.
`action` is `down`, `up`, `drag`, or `move`; `button` is `left` (default),
`right`, or `middle`; `modifiers` is optional and combines Shift = 1, Ctrl = 2,
and Alt = 4 (default 0). A click is `down` followed by `up`. Herdr encodes the
event for the application's mouse mode and drops it when the application has
not enabled mouse reporting, so a plain shell never receives stray input.
`move` reaches only applications that track all mouse motion.
`terminal session observe` opens a read-only live terminal stream for a pane,
terminal, or agent target. It prints newline-delimited JSON `terminal.frame`
records with base64-encoded ANSI bytes, then a `terminal.closed` record when
the server closes the stream. Multiple observers can watch the same terminal
without taking input, resize, scroll, or takeover authority.
On Linux and macOS, an observer is disconnected if a socket write makes no progress
for 30 seconds. A stalled stream can end without a final `terminal.closed` record;
the pane and other clients keep running. Quiet panes do not trigger this timeout.
`terminal title clear` hands the outer terminal window title back to `ui.window_title`.

## Output waits

Wait for output in a pane:

```bash
herdr pane wait-output <pane_id> (--match <text> | --regex <pattern>) [--source visible|recent|recent-unwrapped] [--lines N] [--timeout MS] [--raw]
```

Use `pane wait-output` for normal commands and servers. Use `agent wait` for coding agents.

`pane wait-output` checks the selected snapshot immediately, including output that already exists, then polls until it matches. The default source name is `recent`; matching treats it as unwrapped recent output from the latest 80 rendered terminal rows. `--lines` changes that row limit. `--match` finds a literal substring on one line, and `--regex` uses Rust regular-expression syntax and also matches one line at a time.

A timeout or `agent_prompt_stalled` does not prove the prompt was never delivered. Inspect the agent before retrying.

`pane wait-output` and `agent wait` wait indefinitely when `--timeout` is omitted. For `agent prompt --wait`, both the acknowledgement and the settled-state wait are indefinite when `--timeout` is omitted. A timeout or server error is emitted as JSON on stderr with exit status 1. CLI usage errors exit with status 2.

## Plugins

Plugin commands install and run local executable workflow plugins. A plugin is a manifest plus out-of-process commands; Herdr owns the host surface and plugins own their implementation language.

Install, list, and remove plugins:

```bash
herdr plugin install <owner>/<repo>[/subdir...] [--ref REF] [--yes]
herdr plugin update [<plugin_id|owner/repo[/subdir...]>...] [--yes]
herdr plugin list [--plugin ID] [--json]
herdr plugin uninstall <plugin_id|owner/repo[/subdir...]>
herdr plugin enable <plugin_id>
herdr plugin disable <plugin_id>
```

`plugin install` accepts GitHub shorthand only, such as `ogulcancelik/herdr-plugin-examples/worktree-bootstrap`. It uses `git`, shows a trust preview in interactive terminals, runs supported manifest build commands, and stores GitHub installs in a Herdr-managed directory. Use `--yes` for noninteractive installs. `plugin update` refreshes every GitHub-managed plugin when no targets are given, or only the listed plugin ids or GitHub sources. It preserves each install's requested ref, skips unchanged commits and ignores locally linked plugins during bulk updates. Reinstalling a GitHub-managed plugin creates a new installation directory. Running plugins keep their original files; new invocations use the new installation. Installing over a locally linked plugin is refused. Plugin manifests must declare `min_herdr_version`; install and link fail when the plugin requires a newer Herdr binary. `plugin list` is human-readable by default; pass `--json` for the raw API response.

Plugin installation and enabled state are global to the current user. A plugin installed, linked, enabled, or disabled through one Herdr session is immediately available with the same state in every session.

Local development:

```bash
herdr plugin link <path> [--disabled]
herdr plugin unlink <plugin_id>
```

`plugin link` accepts a plugin directory containing `herdr-plugin.toml` or a direct manifest path. Use it while authoring or testing a plugin from a local checkout. `plugin unlink` and `plugin uninstall` unregister the plugin and leave files in place so running plugins can finish. Updates and reinstalls also retain previous installations; new invocations use the replacement without a config reload. A later successful installation/update or server startup removes obsolete managed installations after the servers using them have exited. Config reload does not release old installations. Plugins must stop detached background processes before their parent command or pane exits; processes surviving server exit are not protected from cleanup. Legacy installations without cleanup tracking and locally linked files are retained. For GitHub installs, uninstall accepts either the plugin id or the same `owner/repo[/subdir...]` shorthand used by install. Actions, event hooks, panes, and link handlers are declared in the manifest; runtime action registration is not part of v1.

Config directory:

```bash
herdr plugin config-dir <plugin_id>
```

`plugin config-dir` prints the plugin's config directory. It creates the directory if needed and seeds it from legacy plugin config locations when present. Use it in setup docs and shell scripts to point users at a stable path for `.env` files and other user-editable config, separate from the managed plugin checkout.

Actions:

```bash
herdr plugin action list [--plugin ID]
herdr plugin action invoke <action_id> [--plugin ID]
```

`plugin action invoke` starts the manifest command for an installed, enabled,
platform-compatible plugin action and prints the started command log record in
the JSON response. Use the qualified action id (`plugin.id.action`) when more
than one plugin uses the same action id. Local action ids cannot contain dots,
so qualified ids remain unambiguous even when plugin ids contain dots.

Logs:

```bash
herdr plugin log list [--plugin ID] [--limit N]
```

Managed terminal panes:

```bash
herdr plugin pane open --plugin ID --entrypoint ID [--placement overlay|popup|split|tab|zoomed] [--width SIZE] [--height SIZE] [--workspace ID] [--target-pane PANE] [--direction right|down] [--cwd PATH] [--env KEY=VALUE] [--focus|--no-focus]
herdr plugin pane focus <pane_id>
herdr plugin pane close <pane_id>
```

`plugin pane open` requires the plugin to be linked, enabled, and compatible
with the current platform. It starts a manifest-declared `[[panes]]` command as
a Herdr-managed terminal pane. The manifest default is `overlay`, which opens a
temporary zoomed overlay over the active pane. It can also open as a split, a
new tab, a zoomed pane, or a session-modal `popup` that does not change the tab
layout. `--width` and `--height` set the outer popup dimensions in terminal
cells or percentages such as `80%`; omitted dimensions default to half the
terminal size, and values smaller than the popup minimum are clamped. A popup
is not a Herdr pane, does not export `HERDR_PANE_ID`, and does not participate
in pane or agent APIs. Native non-terminal plugin panes are outside plugin v1.

New panes identify as `TERM_PROGRAM=herdr`, with `TERM_PROGRAM_VERSION` set to
Herdr's version. They keep `TERM=xterm-256color` and `COLORTERM=truecolor`.
Herdr removes inherited outer-terminal session markers (iTerm2, WezTerm, Kitty,
Windows Terminal, tmux, screen, and Zellij), iTerm2's `LC_TERMINAL` identity,
and known Claude Code, Codex, and OMP session markers before applying explicit
launch environment values. This prevents new panes from claiming the terminal
or agent session that originally started the server. Ordinary environment
variables, including API keys and display settings, remain inherited rather than
being replaced with the attaching client's environment. SSH-agent forwarding has
its own reconnect handling. Existing pane processes are unchanged by this cleanup.

`--env KEY=VALUE` can be repeated on process-launching commands. It applies to the newly launched process only. Herdr-managed variables such as `HERDR_SOCKET_PATH`, `HERDR_BIN_PATH`, `HERDR_ENV`, `HERDR_WORKSPACE_ID`, `HERDR_TAB_ID`, `HERDR_PANE_ID`, `HERDR_PLUGIN_ID`, `HERDR_PLUGIN_ROOT`, `HERDR_PLUGIN_CONFIG_DIR`, `HERDR_PLUGIN_STATE_DIR`, `HERDR_PLUGIN_ENTRYPOINT_ID`, and `HERDR_PLUGIN_CONTEXT_JSON` stay authoritative when they conflict with caller-provided env.

## Read sources

| Source | Meaning |
| --- | --- |
| `visible` | Current rendered screen. Best for UI feedback loops. |
| `recent` | Recent scrollback with terminal wrapping. |
| `recent-unwrapped` | Recent scrollback without soft wrapping. Best for logs. |
| `detection` | Bottom-buffer snapshot used by agent screen detection. |

These meanings apply to reads. For `pane wait-output` only, both `recent` and `recent-unwrapped` search the unwrapped recent snapshot; `recent` remains the default spelling.
