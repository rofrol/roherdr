---
title: Socket API
description: Control a running Herdr server from scripts, tools, and coding agents.
---

Herdr exposes a local socket API for scripts and agents that need to inspect or control a running session.

Most automation should start with the CLI wrappers. Use the raw socket API only when you need direct request/response control or long-lived event subscriptions.

## Choose an integration layer

| Layer | Use it for |
| --- | --- |
| Agent skill | Teaching a coding agent how to use Herdr from inside a pane. |
| CLI wrappers | Shell scripts, simple orchestration, and human debugging. |
| Raw socket API | Custom tools, protocol clients, and event subscribers. |

The layers share the same control surface.

## Schema

The installed CLI can print the socket protocol schema bundled with that Herdr
binary:

```bash
herdr api schema
herdr api schema --json
herdr api schema --output herdr-api.schema.json
```

Plain `herdr api schema` prints a short summary. `--json` prints the full JSON
Schema document for tools, and `--output PATH` writes that document to a file.
The schema covers raw requests, success responses, error responses, emitted
events, and subscription events.

## What you can control

The socket API can:

- create, list, focus, rename, and close workspaces
- create, list, focus, rename, and close tabs
- list, inspect, split, swap, focus, resize, rename, read, close, and send input to panes
- list, inspect, read, prompt, wait on, rename, focus, start, and attach agents through CLI helpers
- report custom agent state from hooks and plugins
- subscribe to events and wait for output or state changes
- install and uninstall built-in integrations
- stop the server and reload config

## CLI examples

Create a workspace:

```bash
herdr workspace create --cwd ~/project --label api
```

Create a tab:

```bash
herdr tab create --label logs
```

Split a pane and run a command:

```bash
herdr pane split w1:p1 --direction right
herdr pane run w1:p2 "npm test"
```

Inspect and rearrange panes:

```bash
herdr pane layout --current
herdr pane neighbor --direction right --current
herdr pane resize --direction right --amount 0.1 --current
herdr pane swap --direction right --current
herdr pane zoom --on --current
herdr pane split w1:p1 --direction right --ratio 0.333
```

Wait for an agent:

```bash
herdr agent wait w1:p1 --until done
```

Read pane output:

```bash
herdr pane read w1:p2 --source recent --lines 50
```

`todo.run`, and `todo.resume` with `action: "retry"`, are refused with the error code `usage_gate` while Claude's usage is high or unknown: the server reads Claude's usage from the provider in that call (not `usage.read`'s cached report) and refuses when a Claude window is 90% or more used or the read fails. The message names each such window with its `used_percent`, or the read's failure. After a refusal the repository's gate stays closed, across server restarts, until such a read shows every Claude window below 80%. `ignore_usage: true`, on the user's word, starts anyway and is recorded in the run's events (see `herdr todo` in the CLI reference).

`todo.resume` with `action: "retry"` takes `task`, the review of the attempt: the next attempt's branch starts from the attempt's commit, which the driver cherry-picks onto the base, and its task is the attempt's with the review appended. A commit that does not cherry-pick is a `retry_conflict` event (`error` names the conflict, `commits` the commit), which takes `retry` without `task` (the attempt starts from the base) or `abort`. `action: "approve"` binds the approval to the last of the answered event's `commits` and the run's base; a branch whose tip differs when the driver reaches the cherry-pick raises a new `review` event (its `error` names both) instead of landing it. The landed commit carries the trailers `Herdr-Item` and `Herdr-Run: <run_id>/<attempt>`, and `picked` names it. `todo.runs` takes an optional `commit` (a sha or a prefix of at least 7 hex digits, the landed commit or the worker's; with `repo`, the directory whose history is read): only the run that landed it, found in the worker store's landings, else by the commit's `Herdr-Run` trailer in `repo`'s history. Its reply then carries `landing`: `landed_sha`, `run_id`, `attempt`, `item`, `worker_commit` and `ts_ms` (from the store), `worker_id` (the attempt's worker, when the store knows it, whose `worker.runs` entry and log are the run's transcript) and `source` (`store` or `trailers`; clients treat an unknown one as `unknown`). A commit no run landed is refused with `todo_run_not_found`, a `commit` that is not hex with `invalid_request`.

`todo.next` (`cwd`, a directory in the repository; optional `chain`, `owner_pane_id`, `owner_session_id`, `workspace_id` and `env`) starts a headless item coordinator for the first open item of `TODO.md`'s `## Next, in order` and returns `item`, `coordinator` (its tenure, with `headless: true` and `worker_id`), `worker` and, with `chain: true`, `chain`. It is refused with `todo_run_active`, `coordinator_active`, `todo_preflight_failed` (no open item, no `TODO.md`) or `usage_gate`. `env` is the caller's environment, which the coordinator's runs' checks, install and push use; the server keeps it in memory only. `todo.stop` (`cwd`) stops the repository's chain and returns `chain`: `repo`, `active`, `owner_pane_id`, `started_ms`, `last_item`, `last_outcome` (`done`, `escalated`, `blocked`, `failed`), `stopped_ms` and `stop_reason`; a repository that never had a chain is refused with `invalid_request`. `coordinator.status` lists a headless tenure with `headless: true` and `worker_id` and no `pane_id`; `history.item` records carry `coordinator_id` and the kinds `coordinator_started` and `coordinator_ended`, which older clients read as `unknown`.

`todo.review` (`run_id`, optional `attempt`, default the run's current one, and `diff`) returns `review`: one attempt as the coordinator reviews it, with `run_id`, `item`, `repo`, `status`, `attempt`, `attempts` (how many the run has had), `worker_id`, `branch`, `base`, `commit` (the one the decision saw, else the verify's head, else the branch's tip), `from_attempt` and `from_commit`, `task` (the worker's first prompt, the run's contract appended), `final_message` (its last reply), `questions` (`request_id`, `tool_name`, `text`, `answer`), `tool_failures` (`kind` `failed` or `denied`, clients treating an unknown one as `unknown`; `tool_name`, `input`, `detail`), `diff_stat`, `diff` (only with `diff: true`), `diff_error` (why the diff could not be read), `verification` (as `worker.verify` returns it), `decision`, `review_text`, `approved` (`commit` and `base`, once approved) and `landed_sha`. A run or attempt that does not exist is refused with `todo_run_not_found`. Clients advertise it as a client method; the Items dropdown asks for it, without `diff`, when an attempt is clicked.

`history.list` (optional `repo`, a directory in it) returns `items`: each TODO item the server recorded, the most recent first, with `repo`, `item`, `title` (from the item's text at its last claim; for an item whose records hold no text, from `TODO.md` while it is still there) and `last`, its latest record. `history.item` (`item`, optional `repo`) returns `item`: its `events` (the records, oldest first) and `runs` (each run they name, with `status`, `created_ms`, `todo_commit` and `attempts`: `attempt`, `worker_id`, `branch`, `commit`, `decision`, `verdict` and `landed_sha`); an item without records is refused with `history_item_not_found`. A record has `id`, `repo`, `item`, `kind` (`claimed`, `noted`, `closed`, `aborted`, `blocked`; clients treat an unknown one as `unknown`), `ts_ms`, `run_id`, `attempt`, `text` (the note, the decision, or why the run was aborted or blocked), `item_text` (the item's text at the claim, or its last text at the close) and `follow_ups` (at a close: the items in `TODO.md` then that were not there at the claim). The server writes the records with the run events that cause them, append-only, in the worker store outside the repository. `history.reconcile` (`repo`) returns `reconcile`: `open_claims` (`item`, `run_id`, `claimed_ms` and the run's `run_status`: claims no other record of their run followed) and `deleted_without_close` (`item`, `title`, `last`: items seen at a claim that are not in the repository's `TODO.md` and have no `closed` record). It reports only. A client shell endpoint also answers `history.list` and `history.item`, advertised in its methods, for the Items list under a coordinator tab; `history.reconcile` stays on the local socket.

`agent.handoff` (`pane_id`, `to`, optional `focus`) hands the session of the agent in `pane_id` over to another agent, for example when the source agent hit its usage limit. `to` is `claude`, `pi` or `codex`. It opens a tab right after the source tab, in the source pane's directory, and starts `to` there with a first prompt: "Continue the work from <agent> session <id>, transcript <path>, task <title>; read it first", what to carry over from the transcript (messages, commands with their output, errors, changed file names, plans) and the provenance (source agent, session id, transcript, repository, revision, time). It is a pointer, not shared context: Herdr never reads the transcript, the new agent does. The session is the one the agent reported, or the one that just exited in that pane; the transcript is Claude's `projects/<cwd>/<id>.jsonl`, Codex's `sessions/…/rollout-…-<id>.jsonl` or Pi's session file, and it must exist on the server's machine. A pane without a known session answers `agent_session_unknown` and a missing transcript `agent_transcript_not_found`, before any tab is created. The source tab stays as it is. It answers like `tab.create`. The TUI offers it as "Hand over to…" in the tab menu; the CLI is `herdr agent handoff <pane> --to <agent>`.

`agent.wait` is server-owned and event-driven. It pins the resolved pane occupant so a replacement cannot satisfy the wait. `agent.prompt` accepts an optional `wait` object with `until` and `timeout_ms`; this submits the prompt and starts the wait in one request, avoiding a race between separate calls. If the resolved agent is already `blocked`, `agent.prompt` returns `agent_blocked` without sending input or starting the wait.

`agent.prompt` returns `prompt_request` (`{"request_id": "...", "state": "accepted"}`) next to `agent`. Herdr follows that prompt through the turn reports of the agent's integration: `pane.report_turn` with `phase: "started"` and the submitted `prompt`, then `phase: "finished"`. The oldest accepted request whose text the started prompt carries becomes `working`, and the next `finished` makes it `finished`; a turn started by other text changes nothing, so a turn already running when the prompt was typed does not finish it. A `started` report with `continuation: true` (Claude's integration sends it for a background task's notification) goes on with the working request's work and changes nothing, so that request ends at the `finished` that follows. An agent whose integration has not reported turns (`pane.report_turn`, or `turn_reports: true` on `pane.report_agent_session`) gets state `unsupported`; herdr never infers turns from the screen. `agent.prompt_status` (`{"request_id": "..."}`) returns the current state with the pane, or `prompt_request_not_found`. `agent.prompt_turn` (`target`, `text`, optional `prefer_workspace_id` and `timeout_ms`) types the prompt and waits until its turn ends; for an agent without turn reports it returns `turn_tracking_unsupported` before typing anything, and an older server rejects the unknown method as `invalid_request`, also before typing. `agent.prompt_tracked` (`target`, `text`, optional `prefer_workspace_id`) types the prompt with the same refusal and answers at once with `prompt_request`. `agent.wait_turn` (`{"request_id": "..."}`) then waits until that request's turn ends and returns `agent_turn_ended` with `reason`: `finished`, `failed` (the integration reported the turn's end with an `error`, Claude's `StopFailure`), `interrupted` (only on an explicit signal: herdr sent the agent Esc or Ctrl-C with `agent.send_keys` while the turn worked and another turn started before its end report, or the integration reported the end with `interrupted: true`), `unknown` (another turn started before this one reported its end, with no signal saying why: the user may have pressed Esc, which Claude reports no `Stop` for, or the agent took a queued message into its work), `exited` (the agent's process ended, its pane exited or closed, or another agent took over the pane's turn reports), or `unknown_request` (the server does not follow that id, for example after a restart). It reads the request and subscribes to its pane's events in one step, so a turn that ended before the wait started answers at once, and it has no timeout. Besides `accepted`, `working` and `finished`, a request's state can be `failed` (with `error`), `interrupted`, `unknown` or `exited`. `pane.report_turn` with `phase: "finished"` takes an optional `error` and an optional `interrupted`, and with `phase: "started"` an optional `continuation`.

`agent.prompt_confirmed` (`target`, `text`, optional `prefer_workspace_id`) types the prompt like `agent.prompt` and answers `agent_prompted` only once the agent shows that it accepted the prompt; `agent.prompt` itself still answers once the submission is written. The acknowledgement is an event, never a duration: for an agent whose integration reports turns, the prompt's request leaving `accepted` (Claude's `UserPromptSubmit` hook reports the turn this prompt started); for any other agent, its state turning `working` after the prompt was typed. An agent already `working` when the prompt is typed has its input open and queues the prompt, so the written submission is its acknowledgement (a prompt typed into a working Pi joins the running turn and is never reported on its own). A dialog on screen before typing answers `agent_blocked`, and an agent still starting `agent_not_ready`, both without typing; a dialog that appears after typing but before the acknowledgement answers `agent_prompt_blocked` with the request id, because the prompt may still arrive once the dialog is answered. The messages name the dialog when screen detection matches a blocking rule (`the "trust_directory" dialog`) or the agent's hook reported a question. Herdr never types the prompt a second time. Without an acknowledgement the call waits, with no timeout, until the agent exits (`agent_not_running`) or the caller closes the connection; a dialog herdr does not recognize therefore keeps it waiting. An older server rejects the method as `invalid_request` before typing anything.

`workspace.move_block` atomically moves the ordered `workspace_ids` before `before_workspace_id`; omit the anchor to move the block to the end. The ids must be unique and the anchor cannot be part of the block. The response contains the authoritative ordered workspace list.

`session.snapshot` returns a one-time bootstrap snapshot for clients that keep
their own local runtime cache. The response includes version/protocol metadata,
focused workspace/tab/pane ids, workspace records, tab records, pane records,
tab layout snapshots, and agent records. It is not a subscription. For cache
bootstrap and recovery, subscribe first, then reconcile through authoritative
reads as described under Event subscriptions below. Events invalidate cached state; they
cannot be unconditionally replayed over a snapshot. Call `session.snapshot`
again after reconnecting or when the local cache may be stale. Attached worktree provenance is included on workspace
records. Full repo worktree discovery remains `worktree.list`.

From the CLI, `herdr api snapshot` prints the live `session.snapshot` response
as JSON for clients and agents that want a simple bootstrap command.

Pane control methods use public pane ids such as `w1:p1`. Methods whose
schema makes `pane_id` optional use the server's active focused pane when it is
omitted. `pane.move` always requires the source `pane_id`.

`pane.send_keys` and `pane.send_input.keys` accept Herdr key-combo strings:
plain printable keys, special keys like `enter` and `esc`, modifier chords
like `ctrl+h`, `control+j`, `alt+x`, and `shift+tab`, function keys like
`f1`, and named punctuation like `minus` and `plus`. They do not accept
`prefix+` binding strings.

```json
{"id":"req_current","method":"pane.current","params":{"caller_pane_id":"w1:p1"}}
{"id":"req_layout","method":"pane.layout","params":{"pane_id":"w1:p1"}}
{"id":"req_neighbor","method":"pane.neighbor","params":{"pane_id":"w1:p1","direction":"right"}}
{"id":"req_edges","method":"pane.edges","params":{"pane_id":"w1:p1"}}
{"id":"req_focus","method":"pane.focus_direction","params":{"direction":"right"}}
{"id":"req_resize","method":"pane.resize","params":{"pane_id":"w1:p1","direction":"right","amount":0.1}}
{"id":"req_zoom","method":"pane.zoom","params":{"pane_id":"w1:p1","mode":"toggle"}}
{"id":"req_input","method":"pane.input.set","params":{"pane_id":"w1:p1","right_click":"pane"}}
{"id":"req_split","method":"pane.split","params":{"direction":"right","ratio":0.333,"right_click":"pane","env":{"HERDR_ROLE":"tests"}}}
{"id":"req_process","method":"pane.process_info","params":{"pane_id":"w1:p1"}}
```

`pane.current` returns a single `PaneInfo`. When `caller_pane_id` is present,
Herdr returns that pane. When it is omitted, Herdr returns the active focused
pane.

`pane.input.set` sets `right_click` to `herdr` or `pane` for one pane. `herdr`
is the default. `pane` forwards unmodified right-click hold and drag gestures
when the application requests terminal mouse reporting; otherwise Herdr falls
back to its pane menu. Right-clicking the pane frame always opens Herdr's menu.
`pane.split` accepts the same optional `right_click` value for the newly created
pane.

`PaneInfo` includes `scroll` when terminal scroll metrics are available:

```json
{
  "offset_from_bottom": 12,
  "max_offset_from_bottom": 240,
  "viewport_rows": 30
}
```

Clients can treat `offset_from_bottom == 0` as at-bottom state.

### Pane graphics

Applications and plugins should emit the standard Kitty graphics protocol through
their pane's terminal output. Herdr manages image placement, clipping, and
visibility in compatible outer terminals.

The external socket pane-overlay API has been removed: `pane.graphics.info`,
`pane.graphics.set`, `pane.graphics.clear`, and `pane.graphics.stream` are no
longer available. There is no replacement socket image API. Internal wire
compatibility with older servers does not restore these public methods.

`pane.layout` returns the tab layout snapshot with `workspace_id`, `tab_id`,
`zoomed`, outer `area`, `focused_pane_id`, pane rects, and split rects/ratios.
`pane.neighbor` and `pane.edges` include that same layout snapshot so clients
can make the next decision without private layout state.

`pane.process_info` returns the pane's shell pid, foreground process group id
when available, and foreground processes with pid, name, argv/cmdline, and cwd
when the platform exposes them.

`layout.export` returns a portable tab layout tree. Omit `tab_id` and `pane_id`
to export the active tab, pass `tab_id` to export that tab, or pass `pane_id` to
export the tab containing that pane.

```json
{"id":"req_export","method":"layout.export","params":{"tab_id":"w1:t1"}}
```

The response includes `workspace_id`, `tab_id`, `zoomed`, `focused_pane_id`, and
`root`. `root` is a BSP tree of `pane` and `split` nodes. Pane nodes can include
`pane_id`, `label`, `cwd`, and argv `command`. Split nodes use
`direction` (`right` or `down`), `ratio`, `first`, and `second`.

`layout.apply` creates a fresh tab from a declarative tree. If `tab_id` is
provided, Herdr creates the replacement tab first and then closes the old tab.
This restores structure, labels, cwd, env, and optional argv commands; it does
not preserve live PTYs, scrollback, or running processes.

```json
{
  "id": "req_apply",
  "method": "layout.apply",
  "params": {
    "workspace_id": "wabc",
    "tab_label": "dev",
    "focus": true,
    "root": {
      "type": "split",
      "direction": "right",
      "ratio": 0.65,
      "first": {
        "type": "pane",
        "label": "editor",
        "cwd": "/repo"
      },
      "second": {
        "type": "pane",
        "label": "tests",
        "cwd": "/repo",
        "command": ["sh", "-c", "just test"],
        "env": { "HERDR_ROLE": "tests" }
      }
    }
  }
}
```

`layout.set_split_ratio` updates an existing split in a tab layout. The response
is `type: "layout_split_ratio_set"` with the updated portable `layout`.

```json
{"id":"req_ratio","method":"layout.set_split_ratio","params":{"tab_id":"w1:t1","path":[],"ratio":0.6}}
```

Process-launching methods accept an `env` object. Herdr applies those key/value
pairs to the newly launched process only. Herdr also injects `HERDR_SOCKET_PATH`,
`HERDR_ENV=1`, `HERDR_WORKSPACE_ID`, `HERDR_TAB_ID`, and `HERDR_PANE_ID` into
managed pane processes. Herdr-managed variables are authoritative when they
conflict with caller-provided env.

`pane.swap` supports directional and explicit forms:

```json
{"id":"req_swap_dir","method":"pane.swap","params":{"pane_id":"w1:p1","direction":"right"}}
{"id":"req_swap_explicit","method":"pane.swap","params":{"source_pane_id":"w1:p1","target_pane_id":"w1:p2"}}
```

Swap is same-tab only. It preserves split shape, split ratios, pane ids, and
running processes. The response is `type: "pane_swap"` with `changed`, optional
`reason`, `source_pane_id`, optional `target_pane_id`, `focused_pane_id`, and
`layout`. Reason values are `no_neighbor`, `same_pane`, `not_found`, and
`cross_tab`. When a tab is zoomed, swap keeps zoom active and mutates the hidden
full-tab layout.

`pane.move` moves a running pane to a different tab, a new tab, or a new
workspace:

```json
{"id":"req_move_tab","method":"pane.move","params":{"pane_id":"w1:p2","destination":{"type":"tab","tab_id":"w1:t2","target_pane_id":"w1:p3","split":"right","ratio":0.5},"focus":true}}
{"id":"req_move_new_tab","method":"pane.move","params":{"pane_id":"w1:p2","destination":{"type":"new_tab","workspace_id":"w1","label":"logs"},"focus":true}}
{"id":"req_move_new_workspace","method":"pane.move","params":{"pane_id":"w1:p2","destination":{"type":"new_workspace","label":"logs","tab_label":"main"},"focus":true}}
```

Existing-tab moves require `split: "right" | "down"`. `target_pane_id` is
optional and defaults to the target tab's focused pane. Same-tab layout changes
remain `pane.swap`; moving to the source tab returns `changed: false` with
`reason: "same_tab"`. Moves involving a zoomed source or target tab return
`changed: false` with `reason: "zoomed_tab"`.

The response is `type: "pane_move"` with `changed`, optional `reason`,
`previous_pane_id`, `previous_workspace_id`, `previous_tab_id`, the moved
`pane`, optional `source_layout`, `target_layout`, optional created workspace or
tab records, optional closed workspace or tab ids, and `focused_pane_id`.
Cross-workspace moves keep the internal pane and terminal alive but assign a new
public pane id in the destination workspace. Subscribers can listen for
`pane.moved`; Herdr does not emit fake pane close/create events for the moved
terminal process.

`pane.zoom` toggles, enables, or disables zoom for the target pane's tab:

```json
{"id":"req_zoom_toggle","method":"pane.zoom","params":{"pane_id":"w1:p1"}}
{"id":"req_zoom_on","method":"pane.zoom","params":{"pane_id":"w1:p1","mode":"on"}}
{"id":"req_zoom_off","method":"pane.zoom","params":{"pane_id":"w1:p1","mode":"off"}}
```

Omitting `pane_id` targets the server's active focused pane. The response is
`type: "pane_zoom"` with `changed`, `zoom_changed`, `focus_changed`, optional
`reason`, `pane_id`, `focused_pane_id`, `zoomed`, and `layout`. `changed` is
true when either zoom state or focus changed. Reason values are `single_pane`,
`already_zoomed`, and `already_unzoomed`.

The CLI wrapper for `notification.show` is:

```bash
herdr notification show "build failed" --body "api workspace" --position top-left --sound request
```

Show a user notification through the configured toast delivery:

```json
{"id":"req_notify","method":"notification.show","params":{"title":"build failed","body":"api workspace","position":"top-left","sound":"request"}}
```

`title` is required and must contain visible text after control characters and repeated whitespace are removed. `body` is optional. Herdr collapses newlines, tabs, carriage returns, and repeated whitespace into spaces, then trims notification text to 80 characters for `title` and 240 characters for `body`. An empty sanitized `title` returns `invalid_params`. `position` is optional and applies only when `ui.toast.delivery = "herdr"`; desktop positions are relative to the full Herdr frame, and omitted positions use `ui.toast.herdr.position`. Terminal, system, and off delivery ignore `position`. `sound` is optional and can be `none`, `done`, or `request`; it defaults to `none` and plays only when the notification is shown.

The response reports whether anything was shown:

```json
{"id":"req_notify","result":{"type":"notification_show","shown":true,"reason":"shown"}}
```

Possible reasons are `shown`, `disabled`, `rate_limited`, `no_foreground_client`, and `busy`. `disabled` means `ui.toast.delivery = "off"`. `busy` means an existing in-app toast was not replaced. Terminal and system delivery are best-effort through the current foreground attached Herdr client.

`notification.show_for_pane` takes the same parameters plus a required `pane_id`, and says what the notification is about. With `ui.toast.delivery = "system"`, clicking the desktop notification focuses that pane, then its tab, then its workspace, whichever still exists. It is skipped while you are looking at that tab, like agent notifications. An unknown pane returns `pane_not_found`. It is a separate method so that an older server rejects it instead of silently dropping the target; fall back to `notification.show` on `unknown method`.

```json
{"id":"req_notify_pane","method":"notification.show_for_pane","params":{"pane_id":"w1:p4","title":"✓ Build","body":"test the new app set","sound":"done"}}
```

`notification.list` returns the notifications the server sent its clients, the last 100, oldest first, kept in memory until the server restarts. Each has an `id` that grows within a server run, `unix_ms`, `kind` (`needs_attention`, `finished`, `update_installed` or `custom`; treat others as custom), `title`, and optional `body`, `agent`, `workspace_id`, `tab_id` and `pane_id`.

```json
{"id":"req_list","method":"notification.list","params":{}}
```

```json
{"id":"req_list","result":{"type":"notification_list","notifications":[{"id":7,"unix_ms":1790640000000,"kind":"finished","title":"claude finished","agent":"claude","workspace_id":"w1","tab_id":"w1:t2","pane_id":"w1:p4"}]}}
```

Click actions exist only where the desktop notifier supports them: on macOS through `terminal-notifier`, and for the local Herdr server.

Set or clear the foreground client's outer terminal window title:

```json
{"id":"req_title","method":"client.window_title.set","params":{"title":"herdr api"}}
{"id":"req_title_clear","method":"client.window_title.clear","params":{}}
```

`client.window_title.clear` hands the title back to `ui.window_title`. The response is
`type: "client_window_title"` with `changed` and reason `set`, `cleared`, or
`no_foreground_client`.

Worktree methods manage Git checkouts as Herdr workspaces. `worktree.create` creates a checkout and returns the new `workspace`, `tab`, `root_pane`, and `worktree` records. If the requested branch already exists locally, it checks out that branch; otherwise it creates the branch from the requested base or `HEAD`. `worktree.create_from_pane` takes the same params plus `pane_id`, and records that pane's tab as the new workspace's creator (`worktree.creator_tab_id` in workspace records); the sidebar nests the worktree under that tab's line. `herdr worktree create` run inside a pane uses it. `worktree.open` opens an existing checkout or returns the already-open workspace. `worktree.remove` runs `git worktree remove` against a linked child workspace and never deletes the branch.

Create a worktree from a source workspace:

```json
{"id":"req_1","method":"worktree.create","params":{"workspace_id":"w1","branch":"worktree/api","focus":false}}
```

Open an existing checkout:

```json
{"id":"req_2","method":"worktree.open","params":{"workspace_id":"w1","branch":"worktree/api","focus":true}}
```

Remove a linked checkout:

```json
{"id":"req_3","method":"worktree.remove","params":{"workspace_id":"2","force":false}}
```

Use at most one of `workspace_id` or `cwd` for `worktree.list`, `worktree.create`, and `worktree.open`; omit both to use the active workspace. Use exactly one of `path` or `branch` for `worktree.open`. Raw socket `cwd` and `path` values must be absolute; the CLI expands relative `--cwd` and `--path` values before sending requests. Workspace responses include optional `worktree` provenance when a workspace belongs to a Herdr worktree group. Worktree commands can emit `workspace.updated` when an existing workspace gains or changes worktree provenance.

Worktree commands also emit lifecycle events. `worktree.create` emits `workspace.created`, `tab.created`, `pane.created`, and `worktree.created`. `worktree.open` emits `worktree.opened`, and it also emits workspace/tab/pane creation events when it opens a new Herdr workspace. `worktree.remove` emits `worktree.removed`; if the linked workspace is still open, it also emits `workspace.closed`.

`workspace.close` rejects closing a primary workspace while linked-worktree workspaces are open unless its params include `"close_group": true`, returning `workspace_group_close_required` when explicit group intent is missing. An explicit group close emits one `workspace.closed` event for each workspace it closes.

## Agent view queries

`agent.view.set` installs one transient declarative projection for the built-in
Agents view. The projection is reevaluated whenever agent facts or current UI
context change. It controls the expanded and collapsed sidebar, mobile Agents
list, mouse targets, indexed focus, and next/previous Agent navigation. It does
not change `agent.list`, notifications, detection, or global attention counts.

Show agents in the currently presented Space or agents needing attention
elsewhere, then order by attention and most recent state transition:

```json
{
  "id": "view_set",
  "method": "agent.view.set",
  "params": {
    "source": "plugin:example.agent-views",
    "label": "focus",
    "filter": {
      "op": "any",
      "filters": [
        {
          "op": "eq",
          "field": "workspace_id",
          "value": {"context": "current_workspace_id"}
        },
        {
          "op": "in",
          "field": "status",
          "values": ["blocked", "done"]
        }
      ]
    },
    "sort": [
      {"field": "attention", "order": "desc"},
      {"field": "state_change_seq", "order": "desc"}
    ]
  }
}
```

Filter nodes use `op` values `all`, `any`, `not`, `eq`, `in`, or `exists`.
Built-in filter fields are `status`, `workspace_id`, `tab_id`, `pane_id`,
`agent`, `seen`, and `state_change_seq`. Use `{"token":"name"}` as a field to
filter plugin-reported pane metadata. Values are strings, booleans, unsigned
numbers, or a context object. Context values are `current_workspace_id` and
`current_tab_id`, and may only be compared to the matching ID field. In a
saved-machine client, the selected server's view applies to the combined agent
list. Current workspace and tab context includes that selected machine, so an
identical ID on another machine does not match; independent filter branches,
such as `status` being `blocked`, still match agents on any connected machine.
Effective status values are `idle`, `working`, `blocked`, `done`, and `unknown`;
`done` means idle and not yet seen.

Sort fields are `workspace_order`, `tab_order`, `pane_order`, `attention`,
`status`, `agent`, `seen`, `state_change_seq`, or `{"token":"name"}`. Sorts are
stable, evaluated in order, and accept `asc` or `desc`. Missing values stay
after present values. When `sort` is omitted, the existing
`ui.agent_panel_sort` policy remains active. A custom sort temporarily replaces
that policy without rewriting config.

`source` identifies the owner. Plugins use `plugin:<HERDR_PLUGIN_ID>`; Herdr
rejects plugin-owned sets when that plugin is missing or disabled. Other callers
may use their own non-`plugin:` source. A successful set atomically replaces the
previous view. The view lasts until it is cleared, replaced, its owning plugin
is disabled, unlinked, or uninstalled, or the server exits. Plugins that want
durable behavior should save the query under `HERDR_PLUGIN_STATE_DIR` and
reapply it from a `[[startup]]` hook.

Clear unconditionally, or only when the named source still owns the view:

```json
{"id":"view_clear","method":"agent.view.clear","params":{}}
{"id":"view_clear_owned","method":"agent.view.clear","params":{"source":"plugin:example.agent-views"}}
```

A source mismatch leaves the active view unchanged. Set and clear responses use
`type: "agent_view"` and report `active`, `source`, and optional `label`.

## Plugin APIs

The plugin API is an early interface for executable workflow tools. A plugin is
a package with a `herdr-plugin.toml` manifest. The manifest declares startup
hooks, shareable actions, event hooks, terminal pane entrypoints, and link
handlers. Startup hooks run once after restore when the API is ready.
Actions and panes are manifest-only; runtime action registration and runtime
argv pane creation are not part of v1.

Installed and linked plugins persist across restarts. Herdr writes a
`plugins.json` registry file alongside `session.json` on `plugin.link`,
`plugin.unlink`, `plugin.enable`, and `plugin.disable`. The
`herdr plugin install` and `herdr plugin link` CLIs also write the same registry
when Herdr is not running, then startup loads it automatically. On startup,
Herdr re-reads each manifest from its original path; if the file is missing or
unparseable, the entry is kept with a `warnings` field so `plugin.list` surfaces
it.

Herdr validates event hook `on` values against known event names at link time.
An unrecognised name does not block the link, but the returned plugin info
includes a warning (e.g. `"unknown event 'worktree.craeted'"`). Check the
`warnings` field in the `plugin.link` and `plugin.list` responses.

Link a local plugin manifest:

```json
{"id":"req_plugin_link","method":"plugin.link","params":{"path":"/path/to/plugin","enabled":true}}
```

`plugin.link` also accepts optional `source` metadata. The CLI uses this when it installs from GitHub so `plugin.list` can show origin, requested ref, resolved commit, and managed checkout path:

```json
{"id":"req_plugin_link","method":"plugin.link","params":{"path":"/managed/plugin/herdr-plugin.toml","enabled":true,"source":{"kind":"github","owner":"ogulcancelik","repo":"herdr-plugin-examples","subdir":"worktree-bootstrap","requested_ref":"main","resolved_commit":"abc123","managed_path":"/data/plugins/github/<managed-checkout>","installed_unix_ms":1780000000000}}}
```

The path can be a plugin directory containing `herdr-plugin.toml` or a direct
manifest path. The manifest shape is:

```toml
id = "example.worktree-bootstrap"
name = "Worktree Bootstrap"
version = "0.1.0"
min_herdr_version = "0.7.0"
description = "Prepare new worktrees"
platforms = ["linux", "macos", "windows"]

[[build]]
command = ["bun", "install"]

[[actions]]
id = "bootstrap"
title = "Bootstrap worktree"
contexts = ["workspace"]
command = ["bun", "run", "bootstrap.ts"]

[[events]]
on = "worktree.created"
command = ["bun", "run", "bootstrap.ts"]

[[panes]]
id = "board"
title = "Worktree board"
placement = "overlay"
command = ["bun", "run", "board.ts"]

[[link_handlers]]
id = "github-issue"
title = "Open GitHub issue"
pattern = "^https://github\\.com/[^/]+/[^/]+/(issues|pull)/[0-9]+$"
action = "bootstrap"
```

`min_herdr_version` is required. The server refuses to link a plugin when the
field is missing, invalid, or newer than the running Herdr binary.

Declare `platforms` at the top level with the OS identifiers (`linux`, `macos`,
`windows`) your plugin supports. Omitting `platforms` is allowed for local
development. `plugin.link` succeeds, but the response includes a warning.
Individual build commands, actions, event hooks, panes, and link handlers can
declare their own `platforms` to override the plugin-level list; if omitted they
inherit from the plugin. Invoking an action or opening a pane whose effective
platforms do not include the current OS returns a `platform_unsupported` error.

List, enable, disable, or unlink linked plugins:

```json
{"id":"req_plugin_list","method":"plugin.list","params":{}}
{"id":"req_plugin_disable","method":"plugin.disable","params":{"plugin_id":"example.worktree-bootstrap"}}
{"id":"req_plugin_enable","method":"plugin.enable","params":{"plugin_id":"example.worktree-bootstrap"}}
{"id":"req_plugin_unlink","method":"plugin.unlink","params":{"plugin_id":"example.worktree-bootstrap"}}
```

Actions are resolved from the linked manifest. `plugin.action.list` returns all actions across installed plugins; pass `plugin_id` to filter.

```json
{"id":"req_plugin_actions","method":"plugin.action.list","params":{}}
{"id":"req_plugin_actions_filtered","method":"plugin.action.list","params":{"plugin_id":"example.worktree-bootstrap"}}
```

`plugin.action.list` returns each action's effective `platforms` after applying
plugin-level inheritance.

Invoke an action by its qualified id or bare action id:

```json
{"id":"req_plugin_invoke","method":"plugin.action.invoke","params":{"action_id":"example.worktree-bootstrap.bootstrap","context":{"invocation_source":"keybinding"}}}
```

`plugin.action.invoke` resolves the manifest action, starts the manifest
command, and returns the Herdr-built invocation context plus the started command
log record. Missing context fields are filled from the active workspace, tab,
focused pane, worktree provenance, and request id. Invoking an action from a
disabled plugin returns a `plugin_disabled` error.

Herdr injects `HERDR_SOCKET_PATH`, `HERDR_BIN_PATH`, `HERDR_ENV=1`,
`HERDR_PLUGIN_ID`, `HERDR_PLUGIN_ROOT`, `HERDR_PLUGIN_CONFIG_DIR`,
`HERDR_PLUGIN_STATE_DIR`, `HERDR_PLUGIN_CONTEXT_JSON`, and available
`HERDR_WORKSPACE_ID`, `HERDR_TAB_ID`, and `HERDR_PANE_ID` values. Action
commands also receive `HERDR_PLUGIN_ACTION_ID`; event hooks receive
`HERDR_PLUGIN_EVENT` and `HERDR_PLUGIN_EVENT_JSON`; pane commands receive
`HERDR_PLUGIN_ENTRYPOINT_ID`.

List recent action and event command logs:

```json
{"id":"req_plugin_logs","method":"plugin.log.list","params":{"plugin_id":"example.worktree-bootstrap","limit":20}}
```

Event hooks run for enabled installed plugins when Herdr emits a matching event
name such as `worktree.created`.

There is no Herdr-managed plugin storage API in v1. `HERDR_PLUGIN_CONFIG_DIR`
and `HERDR_PLUGIN_STATE_DIR` are path discovery only; plugins own their files,
schemas, migrations, and cleanup.

Open a managed terminal UI:

```json
{"id":"req_plugin_pane","method":"plugin.pane.open","params":{"plugin_id":"example.board","entrypoint":"board","placement":"zoomed","target_pane_id":"w1:p1","env":{"HERDR_ROLE":"board"},"focus":true}}
```

`plugin.pane.open` requires an installed, enabled, platform-compatible plugin,
then launches the requested manifest `[[panes]]` entrypoint as an argv-backed
terminal pane. Manifest pane `placement` defaults to `overlay`; request
`placement` overrides the manifest with `overlay`, `popup`, `split`, `tab`, or
`zoomed`. Overlay and popup placements use the active tiled pane as launch
context. Popup terminals are session-modal and do not change the tab layout;
optional `width` and `height` fields set their outer size as terminal cells or
percentages such as `"80%"`. Omitted dimensions default to half the terminal
size, with too-small values clamped to the popup minimum. A popup has no pane
ID, remains outside all `pane.*` and agent APIs, emits no pane lifecycle events,
leaves plugin focus context on the underlying tiled pane, and does not export
`HERDR_PANE_ID` to its process. Popup launch returns `ok`; `popup.close` closes
the active popup and returns
`popup_not_open` when none exists. Split and zoomed panes target an existing
pane; tab panes can target a workspace. Split, tab, zoomed, and overlay panes
behave like normal Herdr panes, and `plugin.pane.focus` and `plugin.pane.close`
continue to operate on those panes.

## Socket transport

Herdr uses newline-delimited JSON over a local socket. On Unix, that socket is a
Unix domain socket. On Windows, it is a named pipe.

Send one request per line:

```json
{"id":"req_1","method":"ping","params":{}}
```

A successful response includes the same `id`:

```json
{"id":"req_1","result":{"type":"pong"}}
```

For request lines that reach JSON decoding, error responses also echo the request's
`id`, including when the method or parameters are invalid. If the JSON is invalid
or has no unambiguous top-level string `id`, the error response uses an empty `id`.
Transport errors, such as invalid UTF-8, can close the connection without a response.

Event subscriptions keep the connection open after the initial response.

## Socket paths

The default socket lives under your Herdr config directory.

Named sessions have separate sockets:

```text
~/.config/herdr/herdr.sock
~/.config/herdr/sessions/<name>/herdr.sock
```

Resolution order:

1. explicit CLI `--session <name>`
2. `HERDR_SOCKET_PATH`
3. `HERDR_SESSION=<name>`
4. default session socket

Use `HERDR_SOCKET_PATH` only for low-level overrides.

For plugins, prefer invoking `HERDR_BIN_PATH` and the CLI wrappers when you need
portable Windows behavior. Raw socket clients are responsible for using the
platform-native local socket form.

## Agent state reporting

Integrations report agent state with `pane.report_agent`.

```json
{
  "id": "req_1",
  "method": "pane.report_agent",
  "params": {
    "pane_id": "w1:p1",
    "source": "custom:docs",
    "agent": "docs-bot",
    "state": "working",
    "message": "building docs"
  }
}
```

`state` carries semantic agent state and affects waits, notifications, and
rollups. Report display-only values separately through metadata.

Session-only official integrations report native session references with `pane.report_agent_session`. State-reporting integrations can still include native session references in `pane.report_agent`. State-independent session reports do not affect waits, notifications, or rollups.

```json
{
  "id": "req_2",
  "method": "pane.report_agent_session",
  "params": {
    "pane_id": "w1:p1",
    "source": "herdr:codex",
    "agent": "codex",
    "agent_session_id": "..."
  }
}
```

An agent that ends its turn by asking the user something (a question, a choice, a confirmation) reports it with `pane.report_awaiting_reply` (`{"pane_id": "w1:p1", "question": "Install now?"}`), usually through `herdr agent awaiting-reply`. The optional `question` is cut once, when reported, to about 40 characters on a character boundary, with escape sequences and control characters dropped; it is kept and dropped with the report, so it never goes stale. The report holds until someone types into the pane (a key press, text or a paste from a client, or `pane.send_text`, `pane.send_keys`, `pane.send_input`, `agent.prompt` or `agent.send_keys`), the agent shows a prompt such as a question form or permission request, or the agent exits or changes session. While it holds, `agent.get` and `agent.list` return `"awaiting_reply": true` whenever the agent is idle; working hides it without clearing it, so an agent that goes on working without a reply shows it again when it stops. Viewing the pane, clicking, scrolling and focus changes do not clear it, and the TUI keeps the agent's Done mark until then. `pane.clear_awaiting_reply` (`{"pane_ids": ["w1:p1"]}`) dismisses the reports of several panes at once, as typing would, without sending input; an unknown pane fails the request and clears none. A later report shows the question again. The TUI offers it as "Dismiss question" in the tab and pane menus.

While an agent waits on the user, `agent.get` and `agent.list` also return `waiting_since_ms` (unix milliseconds since it became blocked, reported its question, or hit a limit) and `question`: the reported question, or while blocked its hook's message. The TUI's `?` list ranks the waiting agents by it, longest first, and shows what each asks under its row.

An agent whose turn a limit ended reports it with `pane.report_limit` (`{"pane_id": "w1:p1", "kind": "usage", "message": "You've hit your limit"}`; `kind` is `usage` for a usage or rate limit that resets on its own, or `credits` when waiting does not help), usually through its integration's hook or `herdr agent limited`. It is held like an awaiting-reply report: shown while the agent idles, cleared when someone types into the pane, by `pane.clear_awaiting_reply`, or when the agent exits or changes session. While shown, `agent.get` and `agent.list` return `limited` with its `kind`, the `message`, and for a usage limit `resets_at` (unix seconds) when Herdr's usage report of the agent's provider has a full window: the latest reset among them. Herdr never resumes the agent by itself.

An agent names the task it works on now with `pane.report_task` (`{"pane_id": "w1:p1", "task": "Fix OAuth callback redirect"}`; whitespace is collapsed, at most 120 characters, no control characters; no `task` or an empty one forgets it), usually through `herdr agent set-task`. `agent.get` and `agent.list` return it as `task`, and with `ui.tab_label = "title"` an unnamed tab shows it ahead of the agent's terminal title, which Claude Code sets only from a session's first prompt. It is dropped when the agent exits or changes session and survives a live handoff.

Both methods accept an optional `resume_argv` array with the command that resumes the reporter's current session after a Herdr server restart. Its first element must be a plain command name, not a path. It allows at most 64 elements and 8 KiB in total, and no element may contain an apostrophe or control character; invalid values fail with `invalid_resume_argv` and the report is not applied. A custom agent must hold the pane through `pane.report_agent` before it can attach a command; otherwise the request fails with `resume_not_accepted`. Herdr keeps the command only while the same `source` and `agent` hold the pane, and it takes precedence over Herdr's built-in resume command for that agent. Older Herdr versions ignore the field.

```json
{
  "id": "req_3",
  "method": "pane.report_agent_session",
  "params": {
    "pane_id": "w1:p1",
    "source": "custom:my-agent",
    "agent": "my-agent",
    "agent_session_id": "...",
    "resume_argv": ["my-agent", "--resume", "..."]
  }
}
```

When an agent's process leaves the pane, Herdr normally forgets its session. A Claude Code session stays saved instead, so a server restart resumes it even when the OS stopped Claude before Herdr (at logout or shutdown) or Claude crashed. When the user ends the session (`/exit`, Ctrl-D, `/logout`), the Claude integration's `SessionEnd` hook calls `pane.forget_agent_session` before Claude exits, and a restart does not resume it. The method needs `seq` and the session (`agent_session_id` or `agent_session_path`); it forgets only that session, and a request older than the pane's latest session report is ignored, so a late request cannot forget a session that was resumed since. A missing session fails with `invalid_agent_session`.

```json
{
  "id": "req_4",
  "method": "pane.forget_agent_session",
  "params": {
    "pane_id": "w1:p1",
    "source": "herdr:claude",
    "agent": "claude",
    "seq": 1791239595599598000,
    "agent_session_id": "..."
  }
}
```

When the OS stops Claude with a signal (for example when the terminal's leftover processes are force-quit), the `SessionEnd` hook calls `pane.report_agent_stopped` with the same parameters instead. Once Claude's process has left the pane and the pane's shell is at its prompt, Herdr types the session's resume command into that shell, spaced by `session.startup_per_agent_delay_ms` when many stop at once, and shows a notice. It does not resume a session that already runs in another pane, one it resumed before that stopped again, or any session when `session.resume_agents_on_restore` is `false`. A question the agent was waiting on (`pane.report_awaiting_reply`) shows again once the same session runs in the pane. The report is ignored unless the session runs in or just exited the pane, and when it is older than that run's last report.

```json
{
  "id": "req_5",
  "method": "pane.report_agent_stopped",
  "params": {
    "pane_id": "w1:p1",
    "source": "herdr:claude",
    "agent": "claude",
    "seq": 1791239595599598000,
    "agent_session_id": "..."
  }
}
```

`pane.get`, `pane.list`, `agent.get`, and `agent.list` expose a read-only `agent_session` object when Herdr has a stored native session reference:

```json
{
  "agent_session": {
    "source": "herdr:codex",
    "agent": "codex",
    "kind": "id",
    "value": "..."
  }
}
```

If no native session reference is stored, the field is omitted. A saved session whose agent has exited is omitted too: nothing runs it until the next restart.

`pane.get`, `pane.list`, `agent.get`, and `agent.list` also expose `foreground_cwd` when Herdr can resolve the cwd of the process currently controlling the pane PTY. The existing `cwd` field remains the pane/workspace cwd used for labels, follow-cwd behavior, and restored session state.

`PaneInfo` and `AgentInfo` expose optional `terminal_title` and `terminal_title_stripped` fields. `terminal_title` is the latest OSC 0/2 title after safety normalization. `terminal_title_stripped` removes one recognized leading activity or spinner glyph and following whitespace. These server-owned values are ephemeral across a cold restart and are independent of the metadata `title` and semantic agent state.

Use `pane.report_metadata` when a user hook wants to customize presentation without taking over lifecycle state from a Herdr integration.

```json
{
  "id": "req_2",
  "method": "pane.report_metadata",
  "params": {
    "pane_id": "w1:p1",
    "source": "user:claude-title",
    "agent": "claude",
    "title": "Refactor auth middleware",
    "display_agent": "Claude: auth",
    "state_labels": {
      "working": "refactoring auth",
      "idle": "ready",
      "done": "review ready"
    },
    "tokens": {
      "summary": "refactor auth",
      "model": "opus"
    },
    "ttl_ms": 3600000
  }
}
```

Metadata reports are display-only. Valid metadata can override the pane title, displayed agent name, visible state labels, and arbitrary named tokens. `working`, `blocked`, `idle`, waits, notifications, and rollups still come from semantic state. Native session restore comes from stored official session references. `agent` is an optional guard for presentation fields against the authoritative agent label; `applies_to_source` similarly guards presentation fields against the active lifecycle authority source. These guards do not apply to token patches: token reporters own clearing and TTL refresh. Use `display_agent` to change the visible name. `state_labels` keys must be `idle`, `working`, `blocked`, `done`, or `unknown`.

Token maps are per-resource patches. A string sets a key, JSON `null` clears it, and omitted keys remain unchanged. The latest accepted update wins. Optional TTL applies independently to token keys updated by that report. Pane tokens are exposed by pane and agent get/list responses and can be rendered as `$name` in Agent sidebar rows. A report may mention at most 16 token keys, and a pane or workspace may retain at most 32 keys. Token names are 1–32 ASCII letters, digits, underscores, or hyphens.

Workspace tokens use the same contract:

```json
{"id":"req_3","method":"workspace.report_metadata","params":{"workspace_id":"w1","source":"user:jj","tokens":{"jj_status":"2 changes","old":null},"ttl_ms":5000}}
```

Workspace get/list responses expose the resulting `tokens` map, and Space sidebar rows can render values such as `$jj_status`. Changes and TTL expiry emit `workspace.metadata_updated` with the latest workspace snapshot. This metadata event is available to API subscribers but does not invoke plugin event hooks.

Presentation text is normalized before storage. Herdr trims surrounding whitespace, removes control characters, and caps `title`, `display_agent`, each state label, and token values at 80 characters. Empty normalized token values clear that key.

`source` and `applies_to_source` are source identifiers. They must be 80 characters or fewer and may contain only ASCII letters, digits, colon, dot, underscore, and hyphen.

Use `ttl_ms` for short-lived metadata. It must be between `1` and `86400000` milliseconds. Omit `ttl_ms` for metadata that should stay until replaced, cleared, or the pane/workspace closes. Presentation fields retain their existing source-scoped expiry behavior; each token updated by the call receives its own deadline. Token metadata is not restored after a server restart.

Use `seq` when a hook may send updates out of order. For the same `source`, reports with a sequence number less than or equal to the last accepted sequence are accepted by the API but ignored by the pane state. A pane or workspace accepts sequenced token reports from at most 32 distinct sources during its lifetime; clearing or expiry does not release those source slots.

## Event subscriptions

Subscribe to events when you need a long-lived stream:

```json
{
  "id": "sub_1",
  "method": "events.subscribe",
  "params": {
    "subscriptions": [
      { "type": "pane.agent_status_changed", "pane_id": "w1:p1", "agent_status": "blocked" }
    ]
  }
}
```

The first response acknowledges the subscription. Later lines are pushed events.
All entries must be valid: if any referenced pane does not exist, Herdr rejects
the entire request with an error and closes the connection. Refresh the pane list
and retry rather than assuming the other entries were subscribed.
Lifecycle subscriptions start when the request is accepted and do not replay
events retained before that point.

Lifecycle and agent-status events are drained in bounded batches, in order within
each subscription. Event history is not durable. If a subscriber falls behind
the retained history, including while its subscriptions are being initialized,
the server sends an error response with the original request `id` and
`error.code: "events_lost"`, then closes that subscription connection instead of
silently continuing with missing events. Other clients remain connected.
The history is shared across event types, so an overrun is reported even when
the evicted events might not have matched this subscription's filters.

On `events_lost`, treat the cached state as stale. Open a new subscription,
wait for `subscription_started`, and keep reading while requesting
`session.snapshot` on another connection. Use authoritative reads to reconcile
current state: replace the cache with the snapshot, and treat incoming events
as invalidation signals that trigger another read. Serialize refreshes and
refresh again if events arrive while a read is in flight.

Snapshots and events have no shared sequence boundary. Ordering is guaranteed
within each subscription entry, not across entries or relative to a snapshot,
so do not unconditionally replay buffered event payloads onto the snapshot.
Recovery restores current state, not the missing event history. Another
`events_lost` requires resubscribing and reconciling again. Slow readers may
need to increase read throughput or reduce event load.

Workspace event subscriptions include `workspace.created`, `workspace.updated`, `workspace.metadata_updated`, `workspace.renamed`, `workspace.moved`, `workspace.reordered`, `workspace.closed`, and `workspace.focused`. `workspace.metadata_updated` reports token changes and TTL expiry without invoking plugin event hooks. Other workspace events describe Herdr UI/runtime lifecycle. `workspace.created` includes optional `workspace.worktree` provenance when the workspace belongs to a worktree group. `workspace.moved` includes the moved `workspace_id`, requested `insert_index`, and updated ordered `workspaces` list. `workspace.reordered` includes the atomically moved `workspace_ids`, optional `before_workspace_id`, and authoritative ordered `workspaces` list. `workspace.closed` includes a final `workspace` snapshot when Herdr can still identify it before removal.
Tab event subscriptions include `tab.created`, `tab.closed`, `tab.focused`,
`tab.renamed`, and `tab.moved`. `tab.moved` includes the moved `tab_id`,
`workspace_id`, requested `insert_index`, and updated ordered `tabs` list for
that workspace.
`tab.set_parent` (`tab_id`, optional `parent_tab_id`) nests a tab under a
top-level tab, and `tab.set_status` (`tab_id`, optional `status`: `running`,
`succeeded` or `failed`) sets a tab's status. Tab objects report them as
optional `parent_tab_id` and `status`; the server keeps children right after
their parent in the tab order, and `tab.close` of a tab with children fails
with `tab_has_children`.
`tab.create_child` (`parent_tab_id`, optional `cwd`, `focus`, `label` and
`env`, as in `tab.create`) creates a tab already nested under a top-level tab,
in that tab's workspace, so it never appears as a top-level tab first; it
answers like `tab.create`. An older server rejects the method, so a caller can
fall back to `tab.create` and `tab.set_parent`.
`tab.create_after` (`after_tab_id`, optional `cwd`, `focus`, `label` and
`env`) creates a top-level tab right after that tab's group (after its job
tabs; from a job tab, after its parent's group), before any client sees it; it
answers like `tab.create`. `workspace.create_after` (`after_workspace_id` plus
the `workspace.create` params) does the same for a workspace, after that
workspace and the rest of its worktree group. The TUI uses both for tabs and
spaces it opens; `tab.create` and `workspace.create` keep appending.
`tab.reopen_closed` (`tab_id` of a tab closed with `tab.close` or by closing
its last pane, optional `after_tab_id`, `focus`) opens it again with its
layout, the names and directories of its panes, and its agents resumed as
after a restart (`session.resume_agents_on_restore`); jobs and running
programs do not come back. It goes after `after_tab_id`'s group, or first.
The server keeps the last 20 closes in memory only, each reopenable once;
otherwise it answers `closed_tab_not_found`. It answers like `tab.create`.
`tab.set_status` also takes an optional `activity` (`idle`): a job runner reports that a
running job has produced no output and used almost no CPU for five minutes; tab objects carry
it as `activity`, and any status change without an activity clears it.
`tab.bookmark` (`tab_id`, `bookmarked`) bookmarks a tab or removes the
bookmark; repeating it is harmless. Tab objects report `bookmarked: true` only
for bookmarked tabs. The bookmark belongs to the tab: it survives a restart,
follows the tab to another space and ends with the tab.
`tab.set_role` (`tab_id`, `role`) says what the tab's agent does for the user:
`coordinator` (works through a list, a repository's TODO, by handing each item
to a worker) or `worker` (does one item, usually in its own worktree); omit or
null `role` to clear it. Whoever opens the tab sets it (`herdr tab role <tab_id>
worker`); it is never derived from the agent's name or title. Tab objects carry
it as `role`, and the sidebar draws `♛` (coordinator) or `⚒` (worker) before the
tab's state. Like a bookmark, it survives a restart and ends with the tab.
The `coordinator` role is a coordination tenure's mark: setting it starts a
tenure for the tab's focused pane (as `coordinator.start` does, refused with
`coordinator_active` when the repository has another coordinator; a pane of the
tab that has a tenure already keeps it), clearing it ends the tab's tenure with
`end_reason` `role_cleared`, and the server marks as `coordinator` exactly the
tabs with a pane bound to an active tenure, so a role set before tenures
existed is cleared.
`coordinator.start` (optional `repo`, a directory in the repository; `pane_id`,
the coordinator's pane, which the CLI sends from `HERDR_PANE_ID`) claims a
repository's coordination: a tenure with its own id (`c-` and 8 lowercase
base32 characters), bound to the pane and its agent session, of the
repository of `repo` or else of the pane's directory (the parent of its git
common directory). One tenure per repository is active at a time; the worker
store's unique index enforces it, also across the two servers of a live
handoff. A second start is refused with `coordinator_active`, naming the
active tenure and its pane, as is a start from a pane that coordinates another
repository; the pane's own active tenure is returned again. It answers
`coordinator` with `coordinator_id`, `repo`, `started_ms`, `epoch` (one more
than the repository's previous tenure), `pane_id` and `session_id`, and once
ended `ended_ms` and `end_reason`. `coordinator.end` (optional `reason`, default
`ended`; `coordinator_id`, else the tenure bound to `pane_id`) ends it and
answers `coordinator`; ending an ended tenure changes nothing, and an unknown
one is refused with `coordinator_not_found`. `coordinator.status` (optional
`repo`) answers `coordinators`, the active tenures, oldest first. A tenure
also ends, with `end_reason` `orphaned`, when its pane closes or its agent
exits, and a server re-evaluates the active tenures' panes when it starts; no
timer ends one. The tenures are recorded as `coordinator_started` and
`coordinator_ended` events in the worker store's event log, with their tables
written in the same transaction. A worker started by a pane bound to an
active tenure carries its id as `owner_coordinator_id`, and so does a
`todo.run` claimed from it; the tenure's `item` is that run's item from its
claim until the run ends (`done` or `aborted`), recorded as
`coordinator_item` events.
What a coordinator owes belongs to its tenure, not to its pane:
`worker.obligations` with `owner_pane_id` lists a tenure's workers under the
pane the tenure is bound to now, and never under another pane, so another
agent session in its old pane inherits nothing. When a coordinator's agent
session comes back (`pane.report_agent_session` with the same session id, as
after `claude --resume`, or `coordinator.start` from it) in another pane, the
tenure stays and its binding moves there: a new binding row, the old one ends,
a tenure that ended `orphaned` is active again while it is its repository's
latest and the repository has no other coordinator, and its workers and runs
move to that pane in the same transaction (`coordinator_resumed`, and an
`owner_moved` event on each worker and `run_owner_moved` on each run).
`coordinator.handoff` (`to_pane_id`; `coordinator_id`, else the tenure bound
to `pane_id`) ends the tenure with `end_reason` `handed_off` and starts the
next one in `to_pane_id`, bound to its agent session, with `epoch` one more,
the old tenure's `item`, and its workers and open runs moved to it, all in one
transaction recorded as a `handoff` event; it answers `coordinator`, the new
tenure. It is refused with `coordinator_not_found` without an active tenure,
with `invalid_request` for the tenure's own pane, with `coordinator_active`
when `to_pane_id` coordinates already, and with `pane_not_found` for an
unknown pane. Only this explicit call hands off; no timer does.
`coordinator.record_override` (`pane_id`, `tool`, `command`, `reason`, optional
`cwd` and `session_id`) records one exception to a coordinator tab's command
allowlist: a tool call that carried `# herdr-override: <reason>` (the Claude
integration's `PreToolUse` hook sends it before it lets such a call run). The
server stores it append-only in the worker store with the pane's active tenure
(`coordinator_id`, its `repo` and `item`; without one, the repository of
`cwd`), cuts the command to its first 4000 characters, notifies the client
shells (`Coordinator override`, with the reason and the command's first line,
no rate limit; it also enters `notification.list`) and answers
`coordinator_override` with `record`: `id`, `ts_ms`, `pane_id`, `tool`,
`command`, `reason`, `repo`, `coordinator_id`, `item` and `session_id`. An
unknown pane is refused with `pane_not_found`, a reason that is empty, not one
line or longer than 500 bytes with `invalid_request`; the hook then denies the
call. `history.overrides` (optional `repo`, a directory in it) answers
`overrides`, the recorded exceptions, oldest first.
`report.record` (`kind`, a slug of lowercase letters, digits and `-`, at most
40; `summary`, one line of at most 500 bytes; optional `uncertain`, `command`,
cut to 2000 characters, `evidence` with `source`, `content` (at most 65536
bytes of the file's text), `bytes` and `truncated`, and `pane_id`,
`session_id` and `cwd`, which default to the pane's agent session and
directory) records one occurrence of a protocol problem. Its fingerprint is
16 hex characters of the SHA-256 of `kind` and the summary normalized:
lowercase, single spaces, and paths, numbers, commit hashes and ids replaced by
`<path>`, `<n>`, `<sha>` and `<id>`. The first occurrence of a fingerprint
creates report `r-N`; later ones add occurrence `K` to it, and one of a closed
report reopens it. Evidence is copied into the worker directory's `reports/`
before the occurrence is written. The report and its occurrences are written
with a `report_recorded` event (whose `worker_id` is `report:r-N`) in one
transaction. A new or reopened report notifies the client shells (no rate
limit; also into `notification.list`), pointing at the pane of the herdr
repository's active coordination tenure (the repository whose `Cargo.toml`
names the package `herdr`), or without a pane when none holds it. It answers
`report_recorded` with `report`, `occurrence` and `notified` (`coordinator
<id>` or `user`; absent for a repeat). A report carries `report_id`, `kind`,
`summary` (the first occurrence's), `normalized`, `fingerprint`, `state`
(`open` or `closed`), `uncertain` (every occurrence was), `first_ms`,
`last_ms`, `count`, `reopened`, while closed `closed_ms`, `closed_by` (the
tenure), `fix` or `not_reproducible`, and `occurrences`: `number`, `ts_ms`,
`summary`, `uncertain`, `repo`, `pane_id`, `session_id`, `coordinator_id`,
`command`, `evidence` (the server's copy), `evidence_source`,
`evidence_truncated` and `reopened` (the closure it reopened). `report.list`
(optional `all`) answers `reports`: the open ones, or all, the latest
occurrence first. `report.close` (`report_id`; `fix`, a TODO item id or a
commit, or `not_reproducible`; `pane_id`) closes it with a `report_closed`
event and answers `report`. It is refused with `report_close_refused` unless
`pane_id` is bound to the herdr repository's active tenure, with
`report_not_found` for an unknown report and with `invalid_request` for a
closed one or a bad `fix`.
Pane event subscriptions include `pane.created`, `pane.updated`, `pane.closed`, `pane.focused`,
`pane.moved`, `pane.exited`, `pane.agent_detected`,
`pane.output_matched`, `pane.agent_status_changed`, and `pane.scroll_changed`.
`pane.focused` also reports manual pane selection changes from any client attached
to this server. It does not move other clients' views, and its payload does not
identify the client. Selecting an already-selected pane does not emit it again.
Terminal-title changes can emit `pane.updated`, but spinner-only raw-title changes do not emit it when `terminal_title_stripped` is unchanged.
`pane.scroll_changed` is scoped to one `pane_id` and emits `pane_id`,
`workspace_id`, and the current `scroll` metrics whenever Herdr observes a
changed scroll snapshot.
Layout event subscriptions include `layout.updated`. The event carries the
updated `PaneLayoutSnapshot` for one tab. Clients maintaining a cache with
`session.snapshot` should use this event to refresh the affected layout through
an authoritative read; a delayed payload may predate their latest snapshot.
`workspace.bookmark` (`workspace_id`, `bookmarked`) does the same for a
workspace; workspace objects report `bookmarked: true`. A workspace's bookmark
and its tabs' bookmarks are separate.

Worktree event subscriptions include `worktree.created`, `worktree.opened`, and `worktree.removed`. Worktree events describe Git checkout lifecycle. `worktree.created` includes the opened `workspace` and created `worktree`. `worktree.opened` includes the target `workspace`, opened `worktree`, and `already_open`. `worktree.removed` includes the `workspace_id`, removed `worktree`, and `forced`.

Use `events.subscribe` for lifecycle events. Dedicated wait helpers are documented separately when a one-shot wait is supported.

## Reading panes

Use `pane.read` through the CLI unless you are writing a protocol client.

```bash
herdr pane read w1:p1 --source visible --lines 80
herdr pane read w1:p1 --source recent --lines 120
herdr pane read w1:p1 --source recent-unwrapped --lines 120
herdr pane read w1:p1 --source detection
```

`recent-unwrapped` is useful for logs because it ignores soft wrapping.
`detection` returns the bottom-buffer snapshot used by agent screen detection.

## Waiting for state

Use waits to coordinate agents and scripts.

```bash
herdr agent wait w1:p1 --until done
herdr agent wait w1:p1 --until blocked
```

Agent waits observe semantic state, not arbitrary command completion.

## Response shapes

Successful responses look like this:

```json
{
  "id": "req_1",
  "result": {
    "type": "pane_info",
    "pane": {
      "pane_id": "w1:p1",
      "terminal_id": "term_abc123",
      "workspace_id": "w1",
      "tab_id": "w1:t1",
      "focused": true,
      "agent_status": "working",
      "revision": 42
    }
  }
}
```

`server.agent_manifests` returns the active agent detection manifest sources and remote update diagnostics without reloading rules:

```json
{
  "id": "req_1",
  "result": {
    "type": "agent_manifest_status",
    "last_check_unix": 1781043522,
    "last_result": "checked",
    "manifests": [
      {
        "agent": "cursor",
        "source": "/home/me/.config/herdr/agent-detection/cursor.toml",
        "source_kind": "local override",
        "active_version": "2026.06.10.1",
        "cached_remote_version": "2026.06.10.1",
        "local_override_shadowing_remote": true,
        "remote_update_result": "current"
      }
    ]
  }
}
```

Fields such as `last_check_unix`, `last_result`, `active_version`, `cached_remote_version`, `remote_update_result`, `remote_update_error`, `remote_last_checked_unix`, and `warning` are omitted when not available. `server.reload_agent_manifests` returns `agent_manifest_reload` with the same `manifests` item shape after reloading the in-memory rule cache.

`server.pty_usage` reports the system's pseudo-terminal usage, sampled at most once a second. `in_use` counts every pseudo-terminal on the machine, not only Herdr's panes; `max` is the kernel limit (`kern.tty.ptmx_max` on macOS, `kernel.pty.max` on Linux). `system` is omitted where the platform has no fixed pool (Windows) or the count cannot be read:

```json
{
  "id": "req_1",
  "result": {
    "type": "pty_usage",
    "system": { "in_use": 108, "max": 511, "required_free": 64 }
  }
}
```

Client shells do not call this method: the server samples the same figure and sends it, with the number of pseudo-terminals its own panes hold, in the snapshot it already streams to them (the sidebar footer's `PTY` line). It also sends a `custom` notification when usage reaches 80% and 90% of `max`, and whenever a new pane finds the pool exhausted.

A new pane must leave `required_free` pseudo-terminals free (64, or a quarter of a smaller pool). Below that, and when the system pool is already full, `workspace.create`, `tab.create`, `pane.split` and the other methods that open a pane fail with the error code `pty_exhausted` and a message such as ``448 of 511 pseudo-terminals in use; close tabs or run `herdr-job clean` ``.

`usage.read` (optional `refresh`, which starts a refresh and still answers the cached report) returns the subscription and API allowance the server last observed, one entry per enabled provider in `providers`, with `status` (`pending`, `ok` or `error`), `observed_at` (unix seconds of the last successful observation) and `error_kind` with an `error` status (`rate_limited`, `auth`, `setup`, `network` or `failed`; clients treat an unknown one as `unknown`). `account` names the login the allowance was read with, so data of the wrong account is visible: `source` (`file:<path>`, `keychain:<item name>`, `env:<variable>`, or `cli:<command>` when the provider's own CLI reads its login), `config_dir` (the CLI's config directory, such as `CLAUDE_CONFIG_DIR` or `CODEX_HOME`), and `email` and `organization` where the provider's data names them (Claude from `oauthAccount` in Claude Code's `.claude.json`, Codex from its app-server's `account/read`). It never carries a token or key. Each rate-limit window (Claude's 5-hour, weekly and model windows, Codex's windows, Gemini's buckets; each on its own, never one combined percentage) has `used_percent`, `resets_at`, `observed_at` and `freshness`: `fresh` when the latest refresh observed it, at most two refresh intervals ago (the provider's own minimum gap when longer), and it has not reset since; `stale` when it is older or its `resets_at` has passed; `failed` when the latest refresh failed, with that refresh's `error_kind`. Only a `fresh` window's `used_percent` is current: a `stale` or `failed` one keeps the last observed value, and its current value is unknown, neither 0 nor 100. A window whose number the provider did not report is left out rather than reported as 0. All these fields are optional; servers without them omit them.

The `worker.*` methods run headless Claude workers that the server owns: `claude -p` over stream-json pipes, with no terminal and no pane. `worker.start` (`cwd`, absolute; `prompt`; optional `model`, `name` and `workspace_id`) spawns the CLI in `cwd` in its own process group, with the user's `CLAUDE.md`, settings and login but the global hooks off (`disableAllHooks`) and the co-author trailer off (`attribution`), a short worker contract appended to the system prompt, and no `HERDR_*` variables in its environment. Bash runs in Claude Code's sandbox (`--permission-mode manual` with per-worker `--settings`: `sandbox.enabled`, `failIfUnavailable`, `autoAllowBashIfSandboxed`, `allowUnsandboxedCommands: false`): it writes only to `cwd` and the worker's temp dir, cannot read credentials (`~/.ssh`, `~/.aws`, `~/.gnupg`, `~/.config/gh`, `~/.claude/.credentials.json`, `~/.git-credentials`, `~/.netrc`, `~/.npmrc`, `~/.docker`, `~/.kube`, `~/.cargo/credentials*`) or any `.env`, `.env.*` or `.envrc` file in `cwd`, and has no network (an empty `network.allowedDomains` with `strictAllowlist`). Deny rules keep `Read` and `Edit` off the same files and turn `WebFetch` and `WebSearch` off. The worker's environment has no credential variables for other services (`GITHUB_TOKEN`, `GH_TOKEN`, `AWS_*`, `GOOGLE_APPLICATION_CREDENTIALS`, `NPM_TOKEN`, `CARGO_REGISTRY_TOKEN`, `AZURE_*`, and names ending in `_TOKEN`, `_API_KEY`, `_SECRET`, `_PASSWORD` and similar); the `ANTHROPIC_*` and `CLAUDE_CODE_*` variables stay, and so do the AWS or Google ones when `CLAUDE_CODE_USE_BEDROCK` or `CLAUDE_CODE_USE_VERTEX` is set. The `started` journal record lists the names removed. The server creates the temp dir new and private (0700) under the journal directory (`tmp/<worker_id>`, in a private `tmp`), refuses the start when anything, a symlink included, is already at that path, names it in the worker contract (the sandbox's own `$TMPDIR` is shared by every sandboxed session of the user) and removes it when the worker's exit is recorded. A worker found `lost` at a server start keeps its temp dir while its process group is alive; a later start removes it once that process is gone. On a platform without the sandbox (anything but macOS and Linux) `worker.start` fails with `worker_unsupported`; on Linux a CLI that cannot start the sandbox exits at once. It answers `worker_info` with a `worker` object: `worker_id` (`w1`, `w2`, ...), `state`, `cwd`, `name` (the given `name`, else the prompt's first line), `workspace_id`, `model`, `pid`, `session_id` (Claude Code's, from `system/init`), `turns`, `last_result` (`subtype`, `is_error`, `terminal_reason`, `api_error_status`, `text`, `failure`, `permission_denials`), `rate_limit` (the last `rate_limit_event`'s `rate_limit_info`), `tool_sessions`, `exit_code`, `exit_signal`, `questions`, `stop_requested_ms`, `takeover_ms`, `degraded` and `journal_path`. `state` is `starting` until `system/init`, then `working`, `waiting_approval` while a tool permission or question is being answered, `finished`, `failed` or `interrupted` from the turn's `result`; a model refusal in the turn (`system/model_refusal_no_fallback`) makes it `failed` even after `result/success`, with `last_result.failure` saying so, and a non-zero exit code right after a `finished` turn (not after `worker.stop`) turns the worker `failed` instead of `exited`, with `exit_code` set and `last_result.failure` saying why. A refusal counts until the turn's `result`, even when a message arrives in between. `last_result.permission_denials` repeats the `result`'s list of denied tool uses. The state turns `exited` when the process ends (or `failed`, above; a worker whose `exit_code` or `exit_signal` is set has ended either way), and `lost` for a worker whose server ended before it did. Clients must treat an unknown `state` as `unknown`.

The server records every line in and out, its permission decisions and the exit as events in the worker store, the SQLite database `<state dir>/workers/workers.sqlite3` (`<state dir>/sessions/<name>/workers/` for a named session, WAL mode). Each event gets a `seq` that only grows, across all workers, and is written in one transaction with the worker's and its questions' state, so the store never holds one without the other. After the commit the event is also appended to the JSONL journal `<worker_id>.jsonl` beside it, with its `seq`; `herdr worker log` reads that export. Workers outlive client restarts; after a server restart they are rebuilt from the store, and a worker that had not exited is marked `lost`. Journals written before the store are imported into it once, at the first start that finds them. A failed store or journal write does not stop the worker: its status carries `degraded` with the error, and a restart may not show what was lost. Tool permissions the CLI asks for are decided by the server's policy, and every decision is journaled. Sandboxed Bash needs no permission, so a `Bash` request arrives only when a user's or project's `ask` rule matches it, and goes to the user. The file tools are not sandboxed: `Read`, `Write`, `Edit`, `MultiEdit`, `NotebookEdit`, `Glob`, `Grep` and `LS` are allowed when the real path of their target is inside the real path of `cwd` or of the worker's temp dir (a symlink that leads outside is denied), and denied with a message to the model otherwise. A `.env`, `.env.*` or `.envrc` file is denied wherever it is (the CLI's `Edit(...)` deny rules already stop the write tools; a `Write(...)` rule did not in 2.1.293). A `Glob` `pattern` or `Grep` `glob` that starts with `~`, has a `..` component, or whose literal prefix resolves outside those roots is denied too. The file tools are not sandboxed and act after this check, so a symlink that Bash swaps in between could still redirect a write; Bash cannot write outside the roots, and the coordinator reviews the worker's diff. A request the auto mode classifier escalates (`decision_reason_type: "classifier"`) goes to the user.

Every other request, and every `AskUserQuestion`, becomes a pending question in the worker's `questions` (`request_id`, `kind`: `approval` or `choice`, `tool_name`, `text`, `reason`, `questions` with each question's `options` and `multi_select`, and `since_ms`) and in the client's `?` list. The worker waits without a time limit. `worker.answer` (`worker_id`, `request_id`, `decision`: `allow` or `deny`, `answers`, `message`) answers the question `request_id` names. `request_id` may be left out only while a single question is pending; with several pending such an answer is refused with `invalid_request`, so an answer cannot reach a question that replaced the one the user read. A `request_id` that is no longer pending is refused with `worker_question_gone`, whose message says what ended it (answered, cancelled, its turn ended, the worker exited or was lost). An approval takes `decision`; an `AskUserQuestion` takes one entry of `answers` per question (an option's label, its 1-based number or free text; a multi-select question's options separated by commas), sent back as the tool's `updatedInput.answers`, or `decision: "deny"` to decline. A question ends without an answer when the turn ends or the worker exits.

Only a `pending` question is answered. An answer goes out through an outbox: its decision is stored as `answer_intent`, which makes the question `answering` (it is then refused with `worker_question_gone` and left out of the `?` list), then the control response is written to the CLI, then `answer_sent` makes it `answered`. A failed write is recorded as `answer_failed`, `worker.answer` fails with the error, and the question is `pending` again, so it can be answered again. A turn end or exit that ends the open questions does not touch one whose answer is in flight: that answer's own outcome settles it. A server that starts and finds an answer still `answering` marks it `expired` (`answer_expired`) when its worker's process is gone; when that process still runs, the worker is reported `degraded` instead. Each question in `questions` carries `state` (`pending` or `answering`), and `settled_questions` lists the most recently ended ones with `request_id`, `state` (`answered`, `cancelled` or `expired`) and `how`. `answered` means the answer was written to the worker's input: the CLI sends no acknowledgement of an answer, and herdr does not record which client was shown a question, so neither is a state of its own.

`worker.status` and `worker.list` report workers; a `worker` object also carries `item` and `repo` (below), `survives_handoff` (true while it runs under a broker that owns its pipes, so a live handoff keeps it running; absent otherwise), `seq`, the `seq` of the worker's latest event, and `turn_seq`, the `seq` of the user message that began its current or last turn. `worker.wait` (`worker_id`, optional `until`: `turn_end`, `exit` or `attention`) blocks until the worker's state changes to the end of a turn (`finished`, `failed`, `interrupted`, `exited`, `lost`) or, with `exit`, to `exited` or `lost`, and answers `worker_info`. With `until: attention` (and optional `after`, a `seq`) it waits until the worker needs its coordinator: a pending question asked after `after`, a turn that ended after `after`, or the worker's end (`exited` or `lost`, which counts however old, since nothing can follow it). It is level-triggered: what is already there answers at once. It answers `worker_attention` with `reason` (`question`, `turn_end` or `gone`; clients treat an unknown one as `unknown`), `questions` (every pending question, with its `request_id`), `worker` and `seq`, the worker's latest event's; passed back as `after`, the same question or turn end does not answer the next wait again, while a later question, even one reusing a `request_id`, does. The wait is woken by the commit of each of the worker's events, never by a timer: it subscribes before it checks (the `seq` it checked is compared again before it blocks, so an event committed in between is not missed); the server only re-checks every few hundred milliseconds whether the caller is still connected. `after` without `until: attention` is refused with `invalid_request`; a server without `attention` refuses it as an unknown `until`. `worker.start` takes optional `owner_pane_id` and `owner_session_id` (the CLI sends the caller's `HERDR_PANE_ID` and `CLAUDE_CODE_SESSION_ID`): the worker's owner, stored with it and reported in the `worker` object with `acked_seq`, the highest `seq` the owner acknowledged. `worker.ack` (`worker_id`, `seq`) records that the owner handled the worker's events up to `seq`, as an `acked` event; it answers `worker_info`. It is idempotent and monotonic: an ack at or below `acked_seq` records nothing, and a `seq` past the worker's latest event is refused with `invalid_request`. `worker.obligations` (optional `owner_pane_id`; every owned worker when absent) answers `worker_obligations` with `obligations`, the owned workers that have an event their owner has not acknowledged, derived from the store's state on every call: `reason` `gone` (the worker ended after `acked_seq`), else `question` (unanswered questions asked after it, listed in `questions`; a question whose answer is in flight counts as handled), else `turn_end` (a turn ended after it), with `worker_id`, `name`, `seq` (the worker's latest event's, which `worker.ack` takes to settle the entry), `owner_pane_id` and `owner_session_id`. Unlike the attention wait, an acknowledged end no longer counts. `worker.stop` and `worker.kill` take an optional `caller_pane_id` (the CLI sends the caller's `HERDR_PANE_ID`); when it is the worker's owner, the signal is journaled with `by_owner` and the exit that follows is acknowledged in the same commit (`acked_seq` becomes the exit's `seq`), so it is no obligation. An exit nobody asked for, or one another pane caused, still is; so is one whose stop came before a server restart. A coordinator acks after handling what a wait or the list returned, never before. A worker without an owner has no obligations. `worker.start` takes an optional `item`, the TODO item the worker works on, as its stable id (`t-` and 8 lowercase base32 characters, `t-abcd2345`); another value is refused with `invalid_request`. The server stores it with the worker and with `repo`, the repository of the worker's directory (the parent of its git common directory, so every worktree of one repository has the same; absent outside git). `worker.runs` (optional `item`, optional `repo`, a directory in the repository) answers `worker_runs` with `items`, one entry per item and repository (`item`, `repo`, `runs`, and `title`, the item's first line in `<repo>/TODO.md` without the box and the id, cut to 80 characters: the one `worker.start` stored with its latest run that has one (read at start, since a finished item leaves the file), else read from the file when listed, absent when neither has it), the one whose first run started first first, so ids of different repositories never mix, and `unassigned`, the runs started without an item, never grouped by name. A run is one worker process; `worker.prompt` adds turns to it. Each run has `worker_id`, `name`, `repo`, `started_ms`, `ended_ms` (absent while it runs), `outcome` (`running`, `finished` or `failed` by its last turn, `exited` when it ended otherwise or in a turn, `lost` when its server ended while it ran, `degraded` when its record is incomplete; clients treat an unknown one as `unknown`), `turns`, `commits` (the shas its turns' replies named on `WORKER-DONE <sha>` lines), `questions` (how many it asked), `journal_path` and `verification`, the latest `worker.verify` verdict (absent when none ran). `worker.verify` (`worker_id`, `base`, `expected_message`, `allowed_paths`, optional `command`, optional `generated`, a list of `path` and `command`) decides whether the worker's commit is ready, so the coordinator does not rely on the worker's `WORKER-DONE` line. The server runs it in the worker's `cwd`, outside the worker's sandbox, and blocks until it ends; nothing in it is timed. Its checks: `commits` (the branch has exactly one commit since `base` and descends from it; `commits` lists each), `message` (each commit's message is `expected_message` alone, no body or trailers), `paths` (`git diff --name-only` from `base` stays within `allowed_paths`, git `:(glob)` pathspecs), `clean_tree` (no changed or untracked file that is not ignored), `processes` (the worker's process has exited, and none of its recorded tool sessions still runs in its directory), then, only when the tree was clean, one `generated` per file (its `command` regenerates it to the committed bytes) and `command` (run with `sh -c`, it exits 0); the tree is restored to its head after them. Each check has `check`, `outcome` (`passed`, `failed`, `unavailable` or `skipped`), `path` for `generated`, and `detail`, the evidence (what failed, the output's last 40 lines). An optional `env` (an object of names to values; the CLI sends its own environment, or none through `--machine`) is the environment the `generated` commands and `command` run with instead of the server's, without its `HERDR_*` variables; without it they run in the server's environment. The `verdict` is `verified` when every check passed, `failed` when any failed, else `unavailable` (a check could not run: git missing, exit 126 or 127, a signal, or a command whose output shows a build-environment error such as a wrong Zig version, a missing cargo subcommand, toolchain or linker, or a shell's `command not found`, with no rustc `error[E...]` or failing test beside it), never a pass; clients treat an unknown verdict or outcome as `unknown`. It answers `worker_verification` with `verification` (`verdict`, `base`, `head`, `commits`, `checks`, `verified_ms`), journaled as the worker's `verification` event and stored with its run; a verification of a directory another one is verifying is refused with `worker_busy`. With `item` only that item's runs are listed and `unassigned` is empty. Workers recorded before `item` existed are unassigned; their start and end times and questions are filled from their stored events, their commits are not. An owned worker's pending question waits quietly for its owner: clients list it as awaiting the coordinator and do not count it as asking the user. `worker.escalate` (`worker_id`, `request_id`) hands it to the user; it answers `worker_info`, records an `escalated` event with its cause, and is idempotent (a question already escalated, or of a worker without an owner, records nothing); a question that is no longer pending is refused with `worker_question_gone`, an unknown one with `worker_no_question`. The server escalates on its own events only, never on a timer: the owner's pane closes or its agent exits (an `owner_gone` event; every later question of that worker is escalated as it is asked), the owner's agent reports a usage or credit limit (`pane.report_limit`) or is blocked (also for questions asked until it works again), the owner's agent goes idle or done while the question is unanswered, and at server start, which re-evaluates each owner pane. Each question in `questions` then carries `escalated`, why; once set it stays. A worker that exits settles its questions instead. A coordinator alive but hung while reported working sends no event, so its questions stay quiet: a known limitation. `worker.start`, `worker.prompt`, `worker.interrupt`, `worker.stop`, `worker.kill` and `worker.answer` take an optional `command_id`, the client's id for that one command (T3 Code's command receipts). The server reserves it in the store's `receipts` table, in the same transaction as the command's first event, and stores the command's outcome with it. A repeated id returns that outcome without running the command again: the same reply, or the same refusal with the same code; a repeated `worker.start` returns the worker it started. A repeat that arrives while the first still runs waits for its outcome. The same id with another method or other parameters is refused with `worker_command_conflict`. An id whose command a server restart cut off before its outcome was stored is refused with `worker_command_interrupted`, naming the worker whose status shows what happened; for `worker.start` the worker it started is returned instead. `worker.take_over` takes no `command_id`: its method shape is frozen for clients, and a second takeover is refused by its claim. `worker.prompt` (`worker_id`, `text`) sends the next turn's message and is refused with `worker_busy` while a turn runs; the check and the message's record happen in one step, so two prompts never both start a turn, and its reply's `turn_seq` is the `seq` of the message it appended. The message is recorded before it is written to the CLI, so a fast reply is never folded in before it; a write that fails is recorded as `input_failed` naming that `seq`. `worker.interrupt` (`worker_id`, optional `turn`) sends the CLI an interrupt control request; the turn then ends as `interrupted`. With `turn` (a `turn_seq`) it interrupts only that turn and is refused with `worker_turn_ended` once that turn has ended, so a repeated interrupt never aborts the next turn; a `turn` the worker never had is refused with `invalid_request`. Its reply's `turn_seq` names the turn it interrupted (absent when none ran). `worker.stop` closes the worker's input, sends SIGTERM to its process group and answers `worker_info` at once; the stop's outcome is the process's exit, which turns the state to `exited`. Until then the worker carries `stop_requested_ms`, so a status asked later shows a worker still alive after the signal; a repeated `worker.stop` sends nothing, and herdr never escalates. `worker.kill` (`worker_id`, optional `force`) sends SIGKILL to the group and to the processes of the worker's recorded `tool_sessions` (Claude Code starts each Bash tool in a session of its own, so these outlive a crashed CLI). A session id is its leader's pid, which a later session leader such as a pane's shell can get, so herdr journals each session with its leader's start time and signals a session only while its leader still has that start time, and of its members only those that did not start before the leader. Sessions journaled without a start time (by older herdr builds) are not verified and not killed. For an `exited` or `lost` worker, whose sessions may have ended long ago, it signals nothing without `force: true` and is refused with `worker_needs_force`, whose message lists what it would kill. It answers `worker_killed` with `worker` and `killed`: `pids` (the processes signalled), `unverified_sessions` and `stale_sessions` (sessions whose leader is gone or is another process now, skipped). `worker.drain` (`action`: `start`, `status` or `cancel`; optional `reason` with `start`) controls the drain before an install: while it lasts, `worker.prompt` and `worker.start` are refused with `workers_draining`, whose message names the `reason`, and nothing else changes (running turns go on, `worker.answer` and `worker.interrupt` still reach them). Starting an active drain keeps it as it was; `cancel` admits turns again. A drain refusal is not stored with a `command_id`, so the same command can be sent again after the drain. The drain is the server's memory only: a server started by a handoff does not drain. It answers `worker_drain` with `drain`: `draining`, `reason`, `started_ms`, `in_turn` (the running workers whose first or prompted turn has not ended, as `worker` objects, without those a live handoff keeps) and `starting` (starts admitted before the drain whose worker is not registered yet; absent when zero). `worker.wait_drained` (optional `in_turn`, the worker ids the previous reply showed in a turn; optional `draining`, the `draining` it showed) blocks until the workers in a turn differ from `in_turn`, the drain starts or ends when `draining` is given, or at once when no worker is in a turn and no admitted start is pending. Woken by the workers' events, never by a timer, it answers `worker_drain` with `ended` added, the workers of `in_turn` no longer in a turn. A client calls it in a loop, passing each reply's `in_turn` and `draining` back, as `herdr worker wait-drained` does. Errors use the codes `worker_not_found`, `worker_not_running`, `worker_busy`, `worker_no_question`, `worker_question_gone`, `worker_needs_force`, `worker_turn_ended`, `worker_unsupported`, `worker_command_conflict`, `worker_command_interrupted`, `workers_draining`, `worker_continuity_gap` (`worker.prompt` and `worker.take_over` of a worker whose output after a server restart is not proven complete; the message names the gap), `invalid_request` and `worker_io_error`. These worker methods are served by the local JSON API socket only, except `worker.runs`, which clients also call when the user opens a coordinator's Items list, and `worker.answer`, which clients call from a question's answer dialog (below).

The client shows each live worker as a line under the space named by `workspace_id` (else the space whose directory holds the worker's), named by its task, with its state; its pending question shows under it and in the `?` list. The client snapshot lists a worker while it runs and, after its end, until its owner acknowledges that end; a worker without an owner leaves at its end. The snapshot also carries `worker_items`, one entry per coordinator tab whose first pane's directory is in a git repository: `tab_id`, `repo` (as `worker.runs` names it), `in_progress` (that repository's items with a running worker) and `attention` (its items with an ended run whose end is not acknowledged), which the tab's Items button shows. An entry also tells the client that `worker.runs` is served to it; the client fetches it with that `repo` when the user opens the list, never in the background. Two methods serve that line and are also advertised to clients: `worker.open_log` (`worker_id`) opens a popup that shows the worker's journal as text and follows it (`herdr worker log --follow`), and `worker.take_over` (`worker_id`) hands the worker's session to a tab. It is refused with `worker_busy` while a question waits on the user, while a takeover runs or once one has opened its tab (an `exited` worker is taken over once too), and with `worker_not_running` for a `lost` worker or one without a session. It marks the worker `takeover_ms`, after which `worker.prompt` and `worker.answer` are refused with `worker_busy`, answers `worker_info` at once, and then, on a thread of its own, interrupts a running turn, waits for its `result`, stops the worker and waits for its exit; only then does it open a tab in the worker's space and `cwd` that runs `claude --resume <session_id>`, so the session never has two writers (a second `--resume` of a running session forks its transcript). Nothing ends the wait on a timer: a worker that ignores SIGTERM keeps the takeover waiting until `worker.kill`. The opened tab is journaled (`takeover_tab_opened`) and reported as `takeover_tab_id`. A takeover that fails (its thread does not start, ending the worker fails, or the tab is not created) releases its claim with a journaled `takeover_failed`, reported as `takeover_error`, so it can be tried again. Each claim has a unique `takeover_id` (reported in the `worker` object): the tab is created with `HERDR_TAKEOVER_ID=<takeover_id>` in its environment and the id in its title. A claim that a previous server left without a recorded tab is looked for at server start and again on a new `worker.take_over`: a tab whose title or pane shell's environment carries the id, or whose pane runs a process resuming the session (`claude --resume <session_id>`), is adopted and journaled as `takeover_tab_opened` with `adopted`, after which takeovers are refused as for any opened tab. When none is found, the claim is reported as `takeover_unfinished` and `worker.take_over` is refused with `worker_busy`, also when a process resumes the session outside herdr's tabs: the previous server may have opened a tab nobody saw, and a second one would be a second writer of the session. `worker.force_take_over` (`worker_id`, served by the local JSON API socket, not advertised to clients) retries it anyway; its new claim replaces the old one under the worker's lock, so concurrent retries are refused while it holds. Older servers' claims have no id; only a resuming process finds their tab. Process environments and command lines are read on Linux and macOS; on Windows only the title finds a tab.

A click on a worker's question in the `?` list, or on the line of a worker that has one, opens an answer dialog bound to that question's `request_id`. Three methods serve it and are advertised to clients. `worker.question` (`worker_id`, `request_id`), asked when the dialog opens, answers `worker_question_detail` with `detail`: `worker_id`, `name` (its task), `cwd`, `state`, `question` (as in `questions`, with `escalated`), `input_text`, the tool's whole input, never cut (a Bash `command` as written with its newlines, then the input's other fields one per line as `key: value`, so a flag such as `dangerouslyDisableSandbox` shows; any other tool's input as indented JSON), `owner_pane_id` and `owner_coordinator_id` when the worker has an owner, and `quiet` while the question still waits for that owner. A question whose answer is being sent or that has ended is refused with `worker_question_gone`, an unknown one with `worker_no_question`. `worker.answer` sends the answer the user clicks. `worker.deny_and_stop` (`worker_id`, `request_id`, optional `message`) denies the question (with `message`, else "The user stopped this worker.") and then stops the worker as `worker.stop` does; a question that is no longer pending does not prevent the stop. It answers `worker_info`. The client sends each of them only on the user's click; whether the question was answered elsewhere or the worker exited while the dialog is open comes from the snapshot's `worker_questions` and `workers`.

`agent.explain` evaluates the target pane's detection snapshot in the running server using the server's active manifest cache:

```json
{
  "id": "req_2",
  "method": "agent.explain",
  "params": { "target": "w1:p1" }
}
```

The response contains the same explain object printed by `herdr agent explain --json`, including the final state, manifest source and version, matched rule, evaluated rule evidence, skip-state reason, idle fallback reason, and `screen_detection_skip_reason` when a full lifecycle hook authority makes screen rules non-authoritative.

Clients need a running server that supports `agent.explain`; after upgrading Herdr, restart or live-handoff the server before relying on this method.

Errors look like this:

```json
{
  "id": "req_1",
  "error": {
    "code": "not_found",
    "message": "pane not found"
  }
}
```

## Protocol stability

The client-rendered Herdr UI uses a stable endpoint generation for local and SSH
servers. Client and server builds do not need to match. During connection setup,
they agree on the core snapshot, screen, input, and blob codecs, and the server advertises
the API methods and optional capabilities it supports. Saved SSH federation requires the
`surface_interest` capability so only the selected machine streams a pane surface and the
`health_check` capability so a quiet broken connection cannot remain Online indefinitely. A server
without this lifecycle support stays at Attention until it is explicitly updated. Other missing methods disable
only those actions and show a client-local notice; they do not disconnect the UI. Rejected
or timed-out actions are also reported without ending the connection. Servers
from before endpoint generation 1 need one final update.

The numbered binary protocol remains for same-install and internal operations,
including direct terminal attach and live handoff. Check `ping` or `herdr status`
before using those operations across different builds. JSON API clients should
ignore unknown fields and handle unsupported methods as normal errors.
